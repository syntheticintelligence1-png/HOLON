## The two changes (the lead's term (b))

Each change is a new version of an existing contract. The old version is unchanged byte for byte, and the sealed
route, every M0-M3 sidecar and the development target use it. The new version is the old one plus one rule, justified
by what the construct means in Solidity.

1. **`holon-sort-types/0.2`: rules U1-U3 for `update`.**
   - Files: `holon/sorts/extracted.py`; `typed_sidecar.py` accepts both versions; `assign.py` walks with the
     sidecar's version.
   - What `update` means: `["update", B, T, v]` is the frontend's write into a member of a local memory value. The
     local held B, and the new value is B with that one member replaced. It is a value, not a storage write: storage
     changes only when the value is assigned back to storage.
   - U1: an update term is a whole struct value, like a struct literal: it names no variable.
   - U2: a member read of such a value resolves by that meaning. It also resolves through `?` branches and chains of
     updates.
   - U3: storing such a value into a whole struct family writes every field, each with its U2 value.
   - 0.1 still refuses `update`.
2. **Extraction `sidecar_version 2`: rule D1** (`holon/frontends/solidity/transitions.py`; `holon/frontends/__init__.py`
   accepts versions 1 and 2).
   - The walk folds an if statement's condition, with an inlined call's parameters bound to its arguments.
   - When the condition is a constant at every reach, a branch that no reach selects is never executed. That branch
     is `dead_code` debt, with the if statement's span, the constant and the number of reaches as its reason.
   - Any other statement the walk never reaches stays unaccounted. G8 is unchanged.

     held-out document, and never in the development document. The pass already treats the neighbouring `calldata`
     and `cdoff` as opaque.

     that, the sort walk completes (486 events). So at the walk level it is the last gap. Whether the full pass,
     disch, derive and the model generator accept the document is untested (P3's prediction was about the model).
2. **The machinery's typed stages have more unrun constructs than the held-out target exposed.** The M3 bundle
   documents (development-side, extracted) stop the sort pass on `pop`, `push` and `abi.encodeWithSignature`. The sort
   pass has only ever run over Morph's one rollup document.
3. **One instrument defect, amended after the outcome existed.**
   - `test_p4_g8` compared coverage.json's top-level `unaccounted`, which is a count, with the key's list `[]`. It
     could never pass.
   - The amendment (`spec/M4/amendments/I50b.jsonl` line 1) compares the statement list with the key, and the count
     with its length. The key is unchanged.
   - P4 is scored on the amended test, and carries that caveat.
4. **I49-R1 flips, as preregistered.** I49's `test_r1_generator_digests_unchanged` compares every generator digest
   with BASE's. All five producer modules are in generator closures, so 15 of the 19 digests move. The flip is the
   re-stamp the lead's term (c) licenses. I50b-R2 predicted it and nothing else; no other sealed test changed outcome.
5. **The prereg commit was re-made once before its first push.** Its first local version's trailer named a model.
   I47's precedent was followed: one soft reset of that unpushed commit. The pushed history has no amend or rebase.
6. **The disclosure log is shared.** I49's R5 needs every holon/ change since the pin disclosed in
   `spec/M4/lib/heldout_disclosures.jsonl`, an I49 file. So I50b appends eight lines to it, as I50 did, and does not
