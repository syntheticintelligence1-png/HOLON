## The wall, and what this key does about it

I118 measured on Aave V3 (contaminated: post-I107) that 3 documents fall back at the typed runner and at bind, covering 6
of its 8 derived laws: in two a value sort is used as a word, in one a term needs a definition the typed model does not
hold (a shift by a constant width). Nothing here was designed from those documents (I never opened them) or from a
corpus entry's code. The rules come from `holon.sorts`, holon-sort-types/0.4, `spec/M3/lib/sort_seeds.json` and the EVM
and Solidity semantics; the fixtures (`tests_m6/fixtures/i123/sol`) are written from the semantics alone.

Reading `holon.sorts.model3` showed where its language stops:
- a typed value (`t:<sort>`, a refined sort's word) is already read as its word by `& | ^ ~`, masks, `trunc`, `sext`,
  `wbyte`, `<<` and `>>` (model3's `to_w`: the payload of the nominal wrapper);
- the IR's `sar`, `sdiv`, `smod`, `addmod`, `mulmod`, `signextend`, `**` and `sfits` have no definition at all;
- an ill-sorted typed `+` or `-` (two typed operands with no affine row) is refused whether or not it is checked;
- `fits` over a plain value (the ABI's validity check of a narrow argument) is refused;
- a section over the typed model (`holon.undo.trace.Trace`, which `holon.gen.symsec`'s SYM section and
  `holon.fact.section` inherit) refuses a term that needs a constant shift the model did not emit: "the term needs
  definitions the typed model does not hold". That is I118's third document's message shape.

## The change (opt-in `typed.sort_ops "word"`)

`holon eval holon` writes `sort_ops: "word"` into the typed sidecar it generates when its protocol names it
(`holon_run.typed_sidecar_keys`; never into a hand sidecar). `holon.sorts.typed_sidecar` accepts only `"word"`.
`holon.sorts.model3.generate` passes it to `build_text`, which sets the generator's `sort_ops`. Without it, every model is
generated byte for byte as before: the new heads are gated in `tx`, and every other hook tests `self.sort_ops`. The rules
live in `holon/sorts/sortops.py`:

| rule | what | source |
|---|---|---|
| W1 | a typed value read as the 256-bit word it occupies by `& \| ^ ~`, masks, `trunc`, `sext`, `wbyte`, `<<` `>>` `sar`, and `+ -` outside checked code; the result an unrefined word | the payload of `T{p: W}` is the word itself |
| S1, S2 | `shl` / `shr`: `["<<", x, n]`, `[">>", x, n]`, 0 when n >= 256 (model3's, unchanged) | EVM SHL, SHR (EIP-145) |
| S3 | `sar`: `x < 2^255 ? shr(x, n) : ~shr(~x, n)`; 0 or all ones past 255 | EVM SAR; Solidity `>>` on a signed type since 0.5.0 |
| C1 | an ill-sorted typed `+`/`-` stays refused when a checked operation of the same action reads it (a panic-17 `fits`/`sfits`); otherwise it is `w_add`/`w_sub` of the words | checked overflow reverts, unchecked wraps |
| R1 | a non-constant shift amount in a document compiled by a release below 0.8.0 is refused | checked on the pinned compilers: 0.5.17 and 0.6.12 accept a signed amount and fail at run time when it is negative (an invalid opcode); 0.7.6 and 0.8 reject it at compile time |
| V1 | `["fits", N, x]` over a value is `x < 2^N`; `["sfits", N, x]` is `sext(N, x) == x`; `sfits` over an operation stays refused | the ABI's validity of a narrow argument |
| D1 | a section over the typed model defines the constant shifts it needs itself, by model3's own builder (with the model's `W` qualified) | the builder is exact by construction (P1 checks it) |

S3 is exact: for a negative x = -1 - y (y = ~x), floor(x / 2^n) = -1 - floor(y / 2^n) = ~(y >> n), and past 255, y >> n
is 0, so the result is ~0. Every pinned solc (0.5.17, 0.6.12, 0.7.6, every 0.8) is 0.5.0 or later, so Solidity's
signed `>>` is `sar` in each. `<<` and `>>` keep the left operand's type and are never overflow-checked; the frontend
already writes the truncation (`trunc` / `sext`), and P1 and P2 confirm it on uint8 and int8.

**Anything else stays refused** (`GenError`), and its document falls back with its laws UNKNOWN: `sdiv`, `smod`,
`addmod`, `mulmod`, `signextend` with a non-constant byte, `**`, `sfits` over an operation, a checked ill-sorted
`+`/`-`, and R1. The coverage of these refusals is recorded (P5) and nothing is guessed.

## Soundness argument

A fallback here can only make a law weaker or UNKNOWN, never wrongly PROVED:
1. **Definitions are the EVM's.** P1 checks every new or reached definition three ways over 641 edge cases (amounts 0,
   1, 7, 8, 255, 256, 257, 300, 2^256 - 1; x in {0, 1, 2, 2^255 - 1, 2^255, 2^256 - 2, 2^256 - 1}; narrow uint8/int8;
   typed Time words): the Python reference from the rules, the code the pinned solc 0.8.24 compiled (run by the pinned
   forge), and the model's own definitions, checked as laws by Bend's evaluation. P2 checks the whole typed model's steps
   (the runner's evaluator) against the compiled code, status and storage, on the same cases and on the pre-0.8 fixtures.
2. **No sort fact comes from a word.** A sort in the typed model is a nominal wrapper over its word, never a predicate on
   it, so reading the word (W1) adds nothing a law could use. A W1 result is an unrefined word and registers no typed
   operation (affine, comparison, realize), which is what SORT's laws read. Where the sort pass asks for a sort fact
   about a word-level result, the model refuses: the `RSignSite` fixture is an unchecked `Time - Time - Time` that the
   sort pass reads as a signed difference with a sign obligation. Stating that obligation from the wrapped word would
   conclude the sign from a word, so the generator raises and the document falls back.
3. **Checked code keeps its discipline (C1).** The wrapping reading applies only to a term no checked operation reads.
   A checked ill-sorted operation stays refused (`RCheckedT`), and a checked operation's revert stays its own `fits`
   check. So a wrapping value never proves a law over checked code. In the other direction, a checked term is never read
   as unbounded: its `fits` is kept exactly as before.
4. **R1 closes an unsoundness the base model has.** Without the opt-in, a non-constant shift in a 0.5 or 0.6 document
   compiles to the EVM shift. A negative signed amount, which reverts on the real code, then reads as a huge unsigned
   amount giving 0, so the model would let the step succeed. Under the opt-in, such documents fall back. (The base's
   behaviour is unchanged; see Questions.)
5. **REFUTED still needs its replay.** Nothing in the change touches replay; P4's true laws hold on the compiled code,
   so a refutation of them would carry a witness that does not replay.

## Surprises

1. **The base typed model already reads typed values as words** for masking and packing. W1's real gap was `+`/`-` on
   ill-sorted typed operands outside checked code, plus the narrow-argument checks (`fits`/`sfits` over a value, V1),
   which refuse every contract with an int8 or uint8 parameter.
2. **`sfits` is outside model3's language entirely**, so any Solidity function with a narrow signed parameter refuses
   its document. V1 is the smallest exact definition; `sfits` over an operation stays refused.
3. **R1's bound is one release line too coarse, and the base model is unsound below it.** On the pinned compilers,
   `uint << int` compiles under 0.5.17 and 0.6.12, and a negative amount fails at run time (an invalid opcode, all gas
   consumed: checked with the pinned forge). 0.7.6 and 0.8.0 reject it at compile time. The prereg and its prompt say
   "below 0.8.0" and "0.5-0.7 accept a signed amount", which is wrong for 0.7. The rule stays as preregistered: it is
   sound, and only coarser, refusing 0.7.x documents (PreVar07 among them) that a 0.7.0 bound would admit. In 0.5 and
   0.6 the base model (without the opt-in) reads a negative amount as a huge unsigned one, giving 0 where the code
   reverts (the soundness argument, 4). The IR term does not record the amount's type, so the opt-in refuses every
   non-constant shift there, Yul ones included.
4. **Three instrument defects, amended before any measured run** (spec/M6/amendments/I123.jsonl):
   - solc 0.5.17 gives inline assembly as text only, so Pre05 lost its Yul function;
   - SortOps's `uncheckedSubT` carries a sign site, so it moved to `RSignSite`, which stays refused (2. of the soundness
     argument);
   - TestSections used Pre05, whose model is refused without the opt-in, so it now uses PreVar05.
5. I117's `test_p6_no_earlier_protocol_names_go_ops` judged later keys; amended in the prereg (spec/M6/amendments/I117.jsonl).
6. **A procedural slip, and a fresh branch.** On `claude/i123-typed-sort-operations`, the first build commit (fed5f466,
   pushed with `[skip ci]`) recorded the two fixture amendments with a `test` field that is not in the audit's
   `file::key` form. `spec/M6/amendments.jsonl` is append-only across history, so that branch's prereg audit could never
   pass again. As I119 did (Q94), I re-committed the prereg unchanged on a fresh branch off the same lead
   (`claude/i123-typed-sort-operations-r2`: 1d61ae98, then the build 5869728b with the lines well-formed). I dropped one
   unpushed local commit on the old branch (7a44e25f, an attempted in-place fix of those lines that the append-only rule
   rejects). The old branch stays as pushed (f37052f8) and unmerged. No measured run had started on either branch
   (only planted-fixture runs while building). `git diff b850ae53 1d61ae98` is empty.
7. **The target-agnostic test caught my harness.** The first local run of `tests_m2.test_target_agnostic_exhaustive`
   failed: `holon/sorts/sortops_diff.py` named "Morph" in a docstring and two error messages of `morph_models_changed`.
   They now say "M3" (the milestone), and the test passes. The function's name stays, since the prereg's test calls it,
   and the test's pattern allows it.
