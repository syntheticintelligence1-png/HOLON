## Done

### 1. `holon/gen/eqsearch.py`: the lemma search (new), wired into `holon.gen.equivalence.prove`

**Order of work.** Each changed definition gets a level: 0 when it reaches no other changed definition, else one more
than the highest level of those it reaches. Definitions are worked in (level, name) order.

**Candidates depend on the obligation alone.** Each class is given only the changed definitions f reaches (all proven
by then); F31's code gave it every proven lemma. Gen's fresh-name counter is reset for each candidate. So the same
obligation gives the same text in any law, any run and any order.

**The proof is deterministic.** The chosen proof of f is the first class, in the fixed order `CLASSES`, whose candidate
bend2 accepts. The order was chosen from observed success: congruence first. On the :363 cone so far, congruence proved
820 of 851, induction 18, eqprove 9, other classes 4. Whether a candidate is accepted depends only on its text and the
lemmas it uses, so batching, workers and the cache cannot change which text wins. The final PROOF.bend lists the
lemmas in (level, name) order. A test checks that one worker or two, batches of 1, 2 or 48, and a cold or warm cache
all give byte-identical laws, proof and per-lemma records.

**Isolation and batching.**
- Candidates are checked in batches, in a small file that holds only:
  - Base, the core block and the libraries;
  - the proven lemmas the batch uses, transitively;
  - the batch itself;
  - imported, a **slice** of the pair module: the items the file reaches, closed under reference. If a slice misses a
    name ("a defined name"), the search falls back to the whole pair module.
- bend2 checks a file in order and stops at its first error. So a failing batch still proves every candidate before
  the failure. The failing candidate is attributed by `Location:`, its kernel message is kept, and it moves on to its
  next class.
- At most two batch files are checked at once. The second includes the first one's lemmas it uses, so its verdict is
  exact either way.
- Batches are 48 definitions while checks are cheap and 256 once a check costs more than 20 s.
- A failure with no location is first retried (up to five times; see bend2's crashes under Surprises). Only then is it
  bisected over the file's prefixes.

**Cache.**
- Proven lemmas are keyed by obligation: sha256 of the generator's text-producing source (`equivalence`, `eqprove`,
  `eqterms`, `eqlib`, `prelude3_lemmas`, and the class order), the core and library text, f, and the text of every
  pair-module item that `q_<f>`'s statement reaches.
- Pair modules built from one model pair give the same key for the same definition. That is "one cone for the shared
  model pair".
- Failed candidates are cached by (key, class, text sha256). A failure named only by bisection is not persisted.
- Storage is in memory and in an append-only JSON-lines file:
  `~/.holon/cache/eqv/<sha256(old model, new model)>/<sha256(bend fingerprint, BendTT kernel sha256, generator)>.jsonl`.
  A run that crashes resumes from it; measured: a killed run restarted with 162, then 848, then 851 cache hits.
  `HOLON_EQV_CACHE=0` keeps the cache in memory only.
- `statement_diff._binding_change` uses this default cache.
- A cached text is used without a candidate check, but it always goes through the final whole-file check. A cached text
  the final check refuses (with a location) is evicted and searched again (`Search.reject`). Tested: a poisoned cache
  entry, a reflexivity "proof" of `w_eq`, is evicted and replaced by the search's own proof. On the planted one-limb
  non-equivalence, the result is REFUTED, never PROVED.

### 2. `holon/statement_diff.py`, `holon/bindings.py`: the statement-hash bridge, and G2's re-check of proof artifacts

**The bridge.** I27's holon-rules/1.3 re-derivation moved the three typed laws' statement hashes (83
`catalog_rederivation` lines, three of them for these laws). Their binding now differs from the bound one (at
`2778fa0`) in `statement_hash` and in the cone. Before this change, no entry kind could cover that combination:
- `binding_change` required an unchanged statement hash;
- a `catalog_rederivation` covers only a hash-only change.

Now:
- A binding_change may carry `"statement_hash": {"old", "new"}`, but only when an **accepted** catalog_rederivation
  line of the same law and milestone maps exactly those two hashes (`catalog_bridge`). That line establishes that the
  claim is the same.
- `scan(..., kinds=("catalog_rederivation",))` checks only those lines, so a binding_change never checks itself.
- `entry_covers` lets such a bridged binding_change cover a rebinding that changes the hash and the cone together, with
  the two hashes compared when known. An unbridged binding_change still never covers a statement-hash change.
- The acceptance record names the bridge line. A committed line is verified against the log at its commit.
- `binding_change_entries` generates the bridge.

**Proof artifacts and G2.**
- An accepted binding_change writes its pair module, LAWS.bend and PROOF.bend (gzip, mtime 0, so deterministic bytes)
  to `spec/bindings/equivalence/<M>/<law>-<proof sha256[:16]>/`.
- G2 checks a committed binding_change line from these artifacts, never by re-searching (`recheck_artifacts`):
  - the files hash to the acceptance record;
  - the laws are exactly the root laws the record names;
  - no file holds an escape hatch;
  - linkage: every BendTT entry of the new model, read at the appending commit, is in the pair module verbatim, and the
    pair's old side hashes to the old binding's cone;
  - bend2 and BendTT (--verdict) accept PROOF.bend again.
- Results are memoized within a process, since G2 scans the log more than once.
- Off git (a copied tree, as in `test_g2_fails_on_an_unaccepted_line_and_on_a_stale_binding`), the same re-check runs
  without the old-side tie, which needs the history.
- **G2's time on such lines is not measured**, because no line could be appended (see Not done). G2's time today on
  the whole milestone is in the table below.

## Surprises

- **bend2's stack overflow is not deterministic, and it is the wall.** A check that takes a minute or more on a large
  lemma file can crash with "the machine stack overflowed" and pass on a rerun of the same bytes. The cause, as far as
  I can read bend2:
  - `term_compare` first tries a rigid comparison that unfolds nothing. When that fails, it compares in full: it
    WHNF-reduces both sides at every node, even where they are syntactically equal.
  - A congruence lemma's first motive is the unfolded body against the folded call. So every such lemma forces a full
    walk of the old side, `o__f(X{..})`, which for a top-of-chain definition is the rest of the transaction.
  - Every lemma file must hold the proven lemmas its batch uses, and those are re-checked each time.

  Bisection on the crash named `s_setPause_9`, a lemma bend2 had accepted earlier in a smaller file. The first version
  of the search treated a bisected crash as a candidate failure and persisted it, which wrongly made `s_setPause_9`
  UNKNOWN. That was fixed (the crash is retried and never persisted), and the bad cache lines were removed by hand from
  my own cache; a backup is in my scratch directory.
- **The real cost is checking proven lemmas again, not failed candidates.** F32 diagnosed N+1 whole-file checks per
  round. With isolation and batching, failed candidates fell to 34 on the whole :363 run. The remaining cost is that
  each file holds about 3 to 8 MB of proven lemmas (congruence motives repeat the whole leaf term; one lemma is
  555 KB), at 1 to 3 minutes per check.
- **I27 moved the typed laws' statement hashes.** `binding_change` could not cover them at all (no entry kind covered
  a hash change together with a cone change). Hence the bridge (Done 2). The task did not foresee this.
- A proof-level let can be named in a rewrite motive, and bend2 unfolds it (probe in `scratchpad/b2-F33/probe2`). That
  is the hook for much smaller congruence proofs (Not done).
- `tests_m2.test_target_agnostic_exhaustive` refuses the identifier `bc` (a local in my first eqsearch version);
  renamed.

## Questions for the human

1. **bend2's stack.** Can the checker run with a larger stack, or can the comparison try the rigid mode on subterms?
   This is outside HOLON's code. The checker command is pinned (GENV), so changing it is your decision. Without that,
   the top-level lemmas of these cones can be checked only after a generator change (item 2).
2. **May an equivalence proof be split across files?** For example, one PROOF.bend per level band, each importing the
   previous band's lemmas, all checked in both kernels. F31's criterion says one PROOF.bend checked whole. Imports are
   checked in the same bend2 process, so splitting alone may not avoid the overflow. I did not change the criterion.

4. The four hand-written lemmas in `prelude3_lemmas.py`, and the Q31 item 1 deviation, are still open from F32.
