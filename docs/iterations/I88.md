What each candidate shows, read with the code at the pin (P3's derivation, written at the prereg):
- **O7.** `ParseBatch` never compares the last decoded context's number with `LastBlockNumber`. At this step the parent is the version-0 genesis, so the start block is the first context's number.
  - With n = 2, the last context is numbered `LastBlockNumber + 1`. The batch passes every check and derives `lastBlockNumber` 3.
  - With n = 1, the one shifted context is also the start block, and the check `lastBlockNumber >= start block` rejects the batch. So the n = 1 candidate at this step is no witness.
- **F11's L1 count.** `ParseBatch` never reads `NumL1Messages` and checks only `txsNum >= l1MsgNum` per block. A context that claims one L1 message derives, while the header's `L1MessagePopped` is 0.
- **O8.** `ParseBatch` never checks that the decoded transactions are used up when the blocks are done.
  - With one transaction in the stream and every context's `txsNum` 0, that transaction is left over.
  - Under `HypC_binds_trailing`, the circuit accepts a step only when nothing is left over. That premise excludes this candidate, and no other candidate is a witness.
- **O24.** A version-0 batch takes its block count and contexts from the calldata argument, which neither the commit's input nor its header holds. The same commit derives block [1] or block [2], depending on that argument alone.

All four are evaluator-level candidates:

### The decider's interface (for I89)

As the coordinator ruled, a function takes a law id and a consumer model and returns the verdict.
- **`holon.derivation.laws.verdict_of(law_id, model=None, root=ROOT)`** reads the committed law file and the law's committed evidence, and returns `verdict(law, evidence, model)`.
- **`verdict(law, evidence, model=None)`** returns `{"status": "UNKNOWN", "attempt": {"engine": "bend", "result": "not_run", "reason": ...}}` when there is no model.
  - A model is any object with `decide(law, evidence) -> {"status", "attempt", ...}`.
  - Its attempt replaces the record's Bend attempt; the evaluator's attempt stays.
  - For a PROVED or REFUTED status, its other keys replace those fields of the record: witness, kernels, checker, artifacts and so on.
- **`evidence`**, which `holon derivation decide` and `verdict_of` build with one function (`holon.derivation.laws.evidence`), holds:
  - the law id;
  - the witness candidate, with its payloads, contexts and compressed data;
  - the observation;
  - the replay entry;
  - the number of candidates, and the number at which the premises hold.
- **Re-deciding in place:** run `holon derivation decide --model MODULE` (it calls `MODULE.consumer_model(root)`), or `holon run --milestone M3 --laws <ids>`.
- **Hypothesis ids:** a record's `model_assumptions` names each hypothesis with every '_' written '-' (`holon.derivation.laws.assumption_id`).

### Design notes for I89 (the consumer's Bend model)

**What is already in Bend.**
- **The committed sides.** Every claim's committed side (`committed:<G>`, `committed_ok:<G>`) and the parent's last block use I24's linked header component: `gen/M3/codec/header_length.json` and its compiled model.
  - Its getters `BatchHeaderBytes_LastBlockNumber` and `BatchHeaderBytes_L1MessagePopped` return `Maybe` bytes.
  - The records' `cone`, `model_sha256` and `compiled_sha256` name exactly that model.
- **The commit step.** The commit premises `is_commitBatch(x)` and `last_ok(step(x, s))` range over the adopted Rollup document's step. Here the evaluator runs it through I85's `Product.commit`. M3's typed Bend model, `gen/M3/sorts/models/morph_rollup.extracted.bend` (I30), steps `commitBatch`.

**The consumer cones** (read off the frozen statements):

| law | consumer terms | `ParseBatch` region |
|---|---|---|
| `L_prod_cycle_lastBlockNumber` | `derive_ok`, `txs_data`, `derived:lastBlockNumber` | the blob check; the parent getters; the start block for version > 0 (the parent's last block, or the first context after a version-0 parent); the no-calldata split; the zero-count check; the decoder; the block loop (Number, `txsNum >= l1MsgNum`, dequeue) |
| `L_prod_count_l1MsgNum` | the same, plus `derived_sum:l1MsgNum` | the same |
| the O8 pair | the same, plus `trailing` | the same. `trailing` is the decoder's count less the blocks' dequeued sum. |
| `L_prod_calldata_BlockContexts` | `derive_ok`, `txs_data`, `derived_blocks` with `contexts` | the version-0 path and the calldata branch: the BE16 count, the length check and the slicing, with `txsData` the whole payload |

No law observes the rest of the entry: the `BaseFee` comparison, the transactions' re-encoding, and the receiver's `SafeL2Data` fill. Before leaving them out of the model, I89 must confirm that none of them can end the entry with an error on the cones' inputs.

**The oracle boundary.**
- **HypB** (`pl(cb(q)) = ok(q)`) is one oracle for the whole blob layer: retrieval over the field elements, concatenation and decompression.
  - The law's blobs are `cb(p)`, so under HypB the consumer sees `p`, and the model never touches the blob bytes.
  - A suggestion for a counter-law: use token functions, `cb(q) = [Tok q]` and `pl([Tok q]) = ok(q)`. Then HypB holds by computation. `vh` must stay consistent with the commit's blob hashes (`blobs_match`).
- **HypT** (`dt(et(u)) = ok(u)`) treats transactions as opaque units. The cones use only the decoded list's length and its slicing per block, so `dt` can answer a count. M2's oracle sidecar names HypT with the same meaning.
- **The HypC pair:**
  - For O8-ignores, `circ = λ_. true` satisfies `HypC_ignores_trailing` by reflexivity, because both sides of its claim are `true`.
  - O8-binds follows from its own premise `HypC_binds_trailing`, instantiated at the law's `s`, `x`, `p` and `ts`, by modus ponens. That needs no unfolding of the consumer.
- **Recorded real answers** for the deferred checks of HypB and HypT against real Go:
  - I85's `results/M3/derivation/environment.json`;
  - I88's `gen/M3/derivation/laws/environment.json` (45 payloads compressed, 62 decompressor answers and 2 decoder answers).

**Witnesses.** `results/M3/derivation/laws/evaluations.json` names each law's evaluator witness, and `gen/M3/derivation/laws/candidates.json` holds its concrete values: the step, the commit members, the payload, the contexts and the compressed data. Each witness's batches were replayed on the real `ParseBatch` (`replay/M3/derivation/laws.json`).
