## Done

### Targets (T0)

- `targets/<name>/target.json`, holon-target/0.1. It holds the target's identity names, its upstream (url, pinned
  commit, watched ref prefix, the refs seen at the pin), its checkout's config key and command-line flag, how its
  documents are extracted, how it is run, its dependency index and where drift writes.
- `targets/morph/target.json` is the development target. It pins 3e44e79 and the 28 tags `git ls-remote` listed on
  2026-11-11 (the pinned commit is no tag). `checkout.vocab` holds the names its milestones' tooling uses: the replay
  report's commit key, the header facts path and model name, the extracted documents' names, the Go module path and
  the replay adapters' checkout entry point.
- `holon/targets.py` reads them. 15 unpinned modules now take every target-specific value from it:
  - `__main__.py`: the `--morph` flags, by the same spelling;
  - `gate.py`;
  - `goreplay.py`, `ownreplay.py`, `hevm_equiv.py`: the report key;
  - `audit/hostile.py`, `gox/replay.py`;
  - `historical/*`: the checkout and the KZG harness's module path, filled in when the harness is copied;
  - `mutate/*`: the checkout and the document names.

  Every output they write is byte-for-byte what it was.

### The toy target (P1)

- `holon target run --target NAME [--jobs N]` (`holon/target_run.py`).
- A machine target runs in a scratch root holding holon/, config/, the target's directory and exactly the spec inputs
  a run reads: the ledger, the shared libraries and the closures' globs, never spec/heldout/. Its laws sit at
  laws/<run.milestone>/ there.
- The run writes run.out and run.gen at the same repo-relative paths, so the records are those of a run in place.
- The toy, abacus, is a two-counter machine under test milestone T11. T47 is already a canary fixture's milestone in
  tests_m2, and T30 or higher would count as typed.

### Parallel run and gate (P2, P3; L20)

- `holon run --milestone M --jobs N` (`holon/parallel.py`):
  - The laws are split into N shards (ProcessPoolExecutor). Each shard runs the unchanged sequential pipeline with
    `--laws`, in a fresh interpreter, into a sibling shard directory.
  - The merge rewrites the shard paths, checks that the shared model/core bytes agree, unions summary and deps, and
    takes splits.json from the shard holding every hypothesis law.
  - Laws stay together with their negation laws, and all hypothesis laws stay in one shard.
  - M0 and the typed milestones are refused with --jobs > 1.
- `holon gate --jobs N` (`holon/gate_parallel.py`):
  - The check groups run in workers: G1 | G8 | G5, G3 | G11..GEVID | G7 | G4.
  - G2's statement-log scan, 146 s of M1's gate, is split by line kind through `statement_diff.scan`'s own `kinds`
    argument and merged in line order. A log holding a line without a string kind is scanned whole.
  - The check workers run at niceness 5, so the scan (the longest path) is not starved: 140 s without that, 117 s
    with it.
- **CPU substitute for the GPU (no GPU here).** Per-law and per-check worker processes on the container's 4 CPUs. No
  GPU enumeration was attempted.

### Performance loop (§9.2(7); R4)

`tools/perf_loop.py (--target NAME | --milestone M) --candidate DIR`:
- A candidate is a directory of replacement files. It is measured against the baseline in fresh copies.
- It is vetoed unless the outputs are the baseline's under G1's normalization (for a milestone: the gate passes with
  the baseline's verdicts).
- A surviving candidate is "kept" at a gain of 5% or more, otherwise "no_gain".
- The tree changes only with --apply.

### Drift trigger (L22; P4, R5)

`holon drift --target NAME [--remote URL]` (`holon/drift.py`):
1. `git ls-remote`, compared on the watched prefix with the pinned refs.
2. If a ref is new or moved, the newest such ref is fetched (depth 1, no blobs) and the documents are re-extracted.
3. A changed document is remodelled by the run's generator. Its kernel index (`bindings.defs_index`) is diffed with
   the committed one.
4. The stale set is the dependents_by_model of every changed definition. stale_closure_latency_s goes to the timing
   file, which is gitignored.

The live run, `results/targets/morph/drift.json`, saw the same 28 tags and reported no change.

## Surprises

1. **My R2 test's outcome list was too broad.** It named spec/M0/ to spec/M3/ whole, which includes the append-only
   amendment logs. So it failed on my own prereg commit, whose M2 amendment the review had asked for. The fix is
   amended: the list now names the fact documents and §0.1's default outcome files.
2. **My P1 test exported too little of the parent tree.** The export held holon/ and config/ only, but every run reads
   spec/ledger/assumptions.json, so the toy failed before deciding a law. The fix is amended: the same parent commit's
   spec inputs are added. The test key first went in with the wrong separator (`Class::method`). The audit flagged it,
   and a second, correctly keyed line was appended, because the log is append-only.
3. **The pinned schema has no room for a vocabulary.** It sets additionalProperties false at the top level, so
   `development` and `vocab` sit inside `checkout` (an open object in the schema).
4. **Two tests fail at BASE already, and I47 does not cause either.**
   - `tests_m2/test_target_agnostic_exhaustive.py` fails at BASE on 4 files. I47 fixes two of them
     (holon/mutate/common.py and stage.py). `fsr` in holon/mutate/replay.py and `bc` in holon/mutate/run.py remain.
   - `tests_m2/test_sorts_unit.py` fails 6 subtests at BASE (Morph names and subprocess in holon/sorts/), unchanged.
5. **The record pins cover far more than the generators.** generator_sha256 reaches 286 holon/ files through
   transitive imports, among them the pipelines, bend.py and the replay adapters. So "ProcessPoolExecutor in the
   pipelines" lives in a new module that drives the unchanged pipeline, not in pipeline.py or mpipeline.py.
6. **Earlier session commit.** The first local prereg commit's trailer named a model. Because it was never pushed, it
   was re-made once without the name (a soft reset of that one unpushed commit) before the first push. The pushed
   history has no amend or rebase.
