## The comparison with §11.3's Impact column

The instrument's `IMPACT` maps 16 REFUTED laws to an O-row. That map is a human reading, and it lives in the tests,
never in `holon/`. Matches: **sink 14 of 16, reach 6 of 16, persistence 4 of 16.** None of the differences was fixed.

**Sink: two differences.**
- **O9 (PAR-init) and O26 (SORT tag).** HOLON says state; §11.3 says finality. In both witnesses every call succeeds:
  - PAR-init: the root write stores a header whose cell 17 is not its cell 9;
  - SORT tag: a copy write stores a value under the wrong ghost tag.

  HOLON's channel stops at the stored value. §11.3 names what that value later breaks (finalization's message
  accounting, and the finality-relevant read of the tag). Tracing a stored register to its later readers would close
  this gap. That is a rule change for a later key.

**Reach: ten differences.** RE3 reads reach as the most privileged class the witness needs (the trust assumption).
§11.3 names the class that triggers or bears the obstruction, and treats the owner's routine actions as environment.
- **O11 x2, O25 x2, O26:** owner against bonded. Every one of these witnesses needs the owner's `revertBatch` before the
  bonded submitter's step.
- **O31 (the onlyOwner external-none law):** owner against challenger. This law's witness is the owner discharging
  the guard.
- **O1:** undecided against owner (genesis). The domain law has no concretization path: BMC was unknown at k = 1.
- **O4 x3:** pending I39 against bonded. The Go-op laws have no node-level path.

**Persistence: twelve differences.**
- **Undecided in eleven:** O9, O11 x2, O22 x2, O25 x2, O26, O27, and O31's two external-none laws. No DISCH class
  decides them: I31's blocking laws for those guards are UNKNOWN, and nothing links an UNDO, FACT, SORT or PAR-init
  divergence to a DISCH basis element yet.
- **O31's blocking law:** dischargeable (I32: the submitter's proveState discharges the challenge-window guard)
  against "until outside action". §11.3 reads the guard from the permissionless committers' side, whose blocking law
  is UNKNOWN on M3.

**Laws with no §11.3 row.**
- **The three codec laws.** Go writes the sequencer-set field (bytes 185..216) where enc_sol writes zeros.
  - §11.6 D1 says the header layouts agree except at byte 0 (O2).
  - On today's code the version byte agrees and this field differs.
  - M0 triaged the same difference (`L_par_hdr_ssvh`) as an intent question; on M3 the records triage it as a finding.
- **The batchDataStore residue law.** It is live through a view (`batchInsideChallengeWindow` answers differently at
  t[0]), where §11.6 D5 lists the BD_i residue as dead. Its Solidity side shows no obstruction, and its filter bin is
  pending.
- **Four DISCH laws**: the external-none laws on the pause guard, the `revertReqIndex` guard and (two) the
  `inChallenge` guard. 3 + 1 + 4 = 8 laws without a row. I81-P3's claim text says "five DISCH laws" there, a slip in
  the frozen key: its count of 8 is right and its test does not check that sentence. The key is left as committed.

## Surprises

1. **Instrument bug: the layout bound** (amendment `tests_m3/_i81.py::layout_bound`, kind instrument_inconsistency,
   commit `12e3165b`).
   - **What the instrument computed.** For a claim of two encoders, it took each side's layout at that side's own
     version premise. The codec laws' Go binder (`h: BatchHeaderV0` or `BatchHeaderV1`) has no version field, so it
     has no such premise, and the function returned None: no upper bound at all. `holon/measures.py`, written
     separately, made the same misreading. The build's first run therefore gave the three codec laws kind bound,
     with no upper bound.
   - **What the key meant.** P1 says the two layouts, "under the law's premises, can differ nowhere else", and the
     contract's M-PAR takes the layouts "at the versions its premises pin". Each codec law pins one version
     (`k.version`). The codec document keys each Go encoder's single layout by that version, and `holon.rules.par`
     derived these very laws by pairing both encoders at the law's version.
   - **The fix.** A side without a version premise of its own takes the law's one pinned version. `holon/measures.py`
     got the same change in the build.
   - **Why the verdict is not moved.**
     - No predicted value changed: the set 185..216 (`SSVH`) and "value 32, certified" are as committed at C_K.
     - Under the bug, the instrument and holon computed no upper bound. That is a non-answer, not a different bound,
       so P1's comparison could not be reached.
     - The corrected bound was computed only after the amendment was committed. It equals the predicted set, and the
       kernel independently agrees: the layout bound is empty on the three PROVED pinned siblings.
   - **For the human to judge.** Had the reader been left as written, `test_p1_par_cc_defects` would have failed with
     no upper bound. Whether that would have counted as a P1 miss is a call on the contract's wording.
2. **Instrument bug: the sorts replay** (amendment `tests_m3/_i81.py::channel_of`, kind instrument_inconsistency,
   commit `12e3165b`).
   - **What the instrument computed.** Rule K5 read each SORT witness run's last model observation as an object
     (`.get("status")`). `replay/M3/sorts/report.json` stores outcome strings ("ok", "rev panic:0x11";
     `holon.sorts.run3`), so it raised AttributeError. `holon/rank.py` crashed the same way at the build's first run.
   - **What the key meant.** K5 is "revert when a witness run of the law ends in a revert on the model". The rule is
     unchanged; the reader now takes an outcome string starting with "rev" as a revert.
   - **Why no prediction's verdict moves.** `channel_of` is used only by R7, the construction cross-check. No
     prediction's test calls it: P3 compares holon's output with the preregistered `EXPECTED` table. The fix turns an
     erroring R7 into a passing one; P3 is the same either way.
3. **Two witness schedules differ from the prereg's guesses** (P4, P6, P7). The commitBatchWithProof kernel witness
   commits a batch with commitBatch in each run first. The commitBatchWithProof attribution witness needs no
   continuation.
4. **The layout algebra agrees with the kernel** on all six encoder-pair laws: an empty bound where Bend PROVED the
   pinned law, 32 positions where Bend accepted the counter-law.
5. **No `L_par_hdr_v2` analogue on M3.** BUILD_PLAN I44's "1 byte position, byte 0" has no M3 instance. The codec
   defect on today's code is the 32-byte sequencer-set field, the opposite of §11.6 D1.
6. **The batchDataStore residue is live through a view only**, against §11.6 D5.
7. **FACT's commitBatchWithProof kernel measure** is exact over I26's domain with one guard left unevaluated
   (`guards[19].reaches[0]`, in the measure's detail). Its 1.0 bits rest on the guards I26 evaluates. The witness
   certifies the lower bound of 1 bit regardless.
8. **A slip in the frozen key's text.** I81-P3's claim counts "five DISCH laws" among the 8 REFUTED laws with no §11.3
   row; there are four. Its test checks the sink classes and the two differing laws, not that sentence, so no verdict
   depends on it.

   obstruction may be either.

   someone regenerates it. That costs about 0.4 s.
