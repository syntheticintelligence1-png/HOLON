### P4, the two unsupported steps

Both are on S1_router:
- step 14: `getVerifier(7, 3)`;
- step 15: `verifyAggregateProof(7, 3, ...)`.

In both, version 7's latest verifier starts at 5 and there is no legacy verifier, so the search loop ends by its head and the call reverts with `ErrorVerifierNotFound`. The real router does exactly that. The evaluator answers "exit term `["exit", ":108-114", "found"]` outside the loop that defines it".

The router's loop record (I19's frontend) has `found` only under `at_break` (value 1) and `exit` (value `["exit", loop, "found"]`). It is not carried, so the record gives no entry value. After a loop that ends by its head, `found` keeps its value from before the loop, but the record does not hold that value (the source's `bool found;` is false). So the step is undetermined, and the evaluator correctly refuses to guess.

The gap is in `holon/frontends/solidity/transitions.py`, a closure file that I80 may not touch. It hides exactly the router's not-found path, which is O3's territory (I37), so a fix should precede I37's laws. Every other compared step agrees in status, revert key, return data, storage, logs and frames.

### P6, the model

**Extensions.** model3's untyped machine compiled 6 of the router's 8 actions. Beyond the storage dynamic arrays the prereg named, it needed two more additive extensions in `holon/bundle2/modelx.py`, both outside every closure (Surprise 4):
- **Whole storage struct values.** model3 refused "a read of a whole struct" for the `Verifier memory _verifier = latestVerifier[_version]` copy. The extension represents it as a record `SR_Verifier{startBatchIndex, verifier}`.
- **The walk's `update` term.** It comes from member assignments on a memory struct.

**Debt.** getVerifier and verifyAggregateProof remain model debt, with model3's own error "exit `found` is not a name of loop :108-114". This is the gap P4 found.

**Refinement.** The model compiles: ALL PROOFS CHECK, and no escape hatch. On its compiled actions, it agrees with the real router on every step but one: S5_rollup_word step 3.
- In that trace, the router's `rollup` word is poked to point at an EOA (`who2addr(5)`), and then `updateVerifier` calls `IRollup(rollup).lastFinalizedBatchIndex()`.

## Surprises

1. **Model fidelity: model3's call success ignores the ABI decoder.** This is S5 step 3, P6's status disagreement.
   - **What the EVM does.** A high-level call to a function with outputs, whose receiver has no code (an EOA), succeeds at the EVM level with empty return data. Solidity's ABI decoder then rejects the data (shorter than the outputs' head), and the caller reverts with empty revert data.
   - **What the compiled model does.** It takes the recorded or chosen answer's `ok` as the call's success, and it reads the missing return bytes as zeros, so the step continues with the value 0:
     - `holon/sorts/model3.py:1153-1157`: `t_callok` is `a_ok(answer)`, the answer's found-and-ok;
     - `holon/sorts/model3.py:1141-1150`: `t_call` is `b_word(a_ret(answer), 0n)`;
     - `holon/sorts/prelude3.py:427-461`: `b_word` reads through `b_take(32n, ..., 0)`, which pads missing bytes with 0;
     - `holon/sorts/prelude3.py:637-649`: `c_find` and `a_ok`.
   - **The evaluator of record** (`holon.extracted_eval`) is half-exposed:
     - `t_callok` (`:1081-1091`) is the answer's `ok`, so a step that only checks the call's success is accepted;
     - a step that reads the value refuses, because `t_call` (`:1061-1079`) decodes with `abi_decode`, whose `_decode_static` raises `Unsupported("ABI data too short")` (`:364-366`). That gives "unsupported", never a wrong answer.
   - **Why it matters.** The frontend's own definition of `callok` ("the call succeeds (does not revert)") includes the decoder in Solidity's semantics of a high-level call. A model that admits a success the code cannot have can produce a REFUTED witness that never replays: a state where a storage address (`submitterContract`, `messageQueue`) names an account without code, and a call "answers" true or a number.
   - **I80's linked machine** gets this step right only because L7 (code-size) catches calls to accounts without code before the record is consulted. A non-member with code that returns short data would still reach the evaluator's refusal above.
   - **Existing M3 records** (checked over the 136 records at the merged lead). Their search runs on model3's compiled model, so they are the exposed ones:
     - REFUTED (24): 19 replay passed, 4 are codec laws with no call (not_run), and 1 replay failed. That one, `L_fact_attr_Rollup_commitState_batchBlobVersionedHashes_batchDataStore_submitter`, has no answer with empty return data in its witness, so it is a different cause, already on record.
     - Only two witnesses (`L_fact_attr_Rollup_commitBatchWithProof_…_submitter` and `L_fact_kernel_Rollup_commitBatchWithProof_committedBatches_blobhash`) hold an `ok` answer with empty return data. Both are `IRollupVerifier.verifyAggregateProof`, which has no outputs, so the empty data is correct, and both replay. No existing REFUTED record depends on the defect.
     - PROVED (87) and UNKNOWN (25): the defect only adds behaviours (a continuation where the EVM reverts) and removes none, so a law proved over the model still covers every real behaviour of this kind. UNKNOWN records are unaffected.
     - Future refutations over call answers are exposed until it is fixed: the refuter may choose "ok, empty data" for a call with outputs.
   - Not fixed in I80, as instructed: it is in closure files.
2. **The zkEVM verifier's extraction exceeds the frontend's term budget** (400000 nodes; `holon/frontends/solidity/transitions.py` TERM_BUDGET). It fails within a second, so it is not a time problem. The 1100-line Plonk Yul (nested functions, about 180 mstores, memory pointers) builds terms past the budget. The circuit stays named debt. HypC (I37) does not need its document, since the harness answers `verifyBatch` with stand-ins.
3. **The frontend's loop records omit the entry value of a break-only local** (P4's two steps, P6's two debt actions). The router's `found` is assigned only on the break path. When its loop ends by its head, neither machine can determine `found` from the document. This is a frontend gap (a closure file), not an evaluator one. It hides the router's not-found path, which O3 (I37) is about.
4. **The model extension needed more than the prereg named.** The prereg named storage dynamic arrays. model3 also refused whole struct values and the `update` term, so the extension handles them too, under the same rule (outside every closure). The adopted Rollup's typed and untyped model texts regenerate byte for byte (R1).
5. **A generated extraction sidecar cannot be loaded by `holon.frontends.load_sidecar`**, which requires an output ending `.extracted.json`. The contract fixes `gen/M3/bundle2/documents/<member>.json`. So `holon/bundle2/members.py` checks the sidecar with the Solidity frontend's own rules and computes the compiler information itself, as `holon.machine.toolchain_info` does. `holon extract solidity --sidecar gen/M3/bundle2/sidecars/router.json` would refuse.
6. **R1's init.json.** Since F40, `holon run` writes `gen/M3/sorts/models/morph_rollup.extracted.init.json` with the deployment's code table, which `holon model` does not write. So the comparison of a fresh `holon model` with the committed init.json fails at the base. Found while drafting the prereg, so R1 compares the model texts only. This is disclosed in the key.
7. **Forge's state-diff `reverted` flag** is set for a frame whose enclosing frame reverted (toy test before the prereg). L8's "persisted" follows that flag.
8. **The harness records no member's call to itself** (C2: "to an account other than itself"). S5 step 1, `rollup` poked to the router itself, is handled by the linked machine's dispatch (no such selector, so it reverts) and agrees. The model's refinement of that step agrees too.
