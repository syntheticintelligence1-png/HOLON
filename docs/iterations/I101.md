## F-M3-37: the evidence a counted round carries

**The rule** (`spec/M3/lib/audit_evidence.json`, now `holon-audit-evidence/0.2`). F-M3-27's header rule is unchanged:
its finding, its four records and their version fields are what `tests_m3/test_audit_evidence.py` E5 pins. Each record
also carries its content now:

| Record | Content (`holon/audit/rounds.py` `content_problems`, read by RD2 and CV1) |
|---|---|
| `a1.json` | at least one mutant that ran: a verdict other than `refused` |
| `a2.json` | at least one case that ran: a verdict other than `unsupported` |
| `a4.json` | valid against `spec/M3/lib/audit_a4.schema.json`; its laws exactly `packet.json`'s; its `counts` the tally of its laws' `class` |
| `packet.json` | valid against `spec/M3/lib/audit_packet.schema.json`; at least one law |

The schemas describe the records `holon audit vacuity` and `holon audit hostile` write. Rounds 1-9's `a4.json` and
`packet.json` are all valid against them. A problem names F-M3-37, beside F-M3-27 in RD2's reason.

**The rebuild.** `holon audit evidence --milestone M --rebuild [--rounds streak|all|n,..] [--only a4|packet]`
(`holon/audit/evidence.py`) rebuilds each round's `a4.json` (`holon audit vacuity --check`) and `packet.json`
(`holon audit hostile --check`) from the round's own target commit, byte for byte.
- By default it rebuilds the rounds of the current streak (`results/<M>/audit_status.json`), on which the converged
  verdict rests.
- CI runs it on M3 in a job of its own, `audit-M3-evidence`.
- `a1.json` and `a2.json` are checked, not rebuilt: `holon audit mutation --check` and `hostile-input --check` are never
  run unattended.
- Each rebuild materializes the target's tree (about 575 MB), and frees it before the next one.
- **What the rebuild pins.** A rebuild runs HEAD's tools (`holon/audit/vacuity.py`, the packet builder in
  `holon/audit/hostile.py`) over the target's inputs, as `--check` always has. So a later change to those tools that
  alters a counted round's record turns `audit-M3-evidence` red. That is intended: the instruments that made counted
  evidence must keep reproducing it. A tool change that is meant to classify differently needs a new record version
  for later rounds, with the old rounds still rebuilt as they were.

## F-M3-42: a subset run keeps what it does not own

The pipeline is not edited: its bytes are in every committed record's `generator_sha256`. Instead, the command line
(`holon/__main__.py`'s `cli`, which `python -m holon` calls) runs any `run` with `--laws` inside `holon/subset.py`
`keep()`, as I47's `holon/parallel.py` wraps the pipeline from outside:
- Before the run, `keep()` reads the files under the run's `gen/<M>/model` and `gen/<M>/core`, and its `summary.json`
  and `deps.json`.
- After the run, it writes back each of those files the run removed. It writes nothing the run wrote.
- When the run rewrote `summary.json` or `deps.json`, it merges them: the earlier entries, with the listed laws' entries
  replaced by the run's (`deps.json` in `holon.bindings.dump`'s format).

A run without `--laws` never enters it, and `main()` itself is unchanged. `--jobs` workers write into fresh shard
directories, so their own `keep()` has nothing to keep, and the outer run's merges. No generator closure changes: B9 checks each IR version's
`holon.records.generator_files`, `holon.profile.generator_files` and the bundle-law closure.

In a detached worktree of HEAD (`OUT/subset.json`), each run exits 0 with its laws PROVED. Each deletes nothing, leaves
`summary.json` and `deps.json` byte-identical, and changes only the listed laws' records:
- the finding's law `L_par_rt_BatchHeaderV0_Bytes_BatchHeaderBytes_Version_v0` alone;
- that law with its v1 sibling.

At the base the same one-law run deleted the five model files and cut `summary.json` from 12 entries to 1.

## Surprises

- **The prereg audit refused the schemas under `spec/schemas/`.** A prereg input lives under `spec/<M>/lib/`,
  `spec/lib/` or the key's own paths. They moved beside the rule before the prereg was pushed: the pushed prereg is
  the corrected commit.
- **A first draft of B5 would have passed vacuously.** The template wraps "Only a" and "`different`-family round" onto
  two lines, so an `assertNotIn` on the sentence passed whatever the prompt said. The test flattens whitespace first.
  This was found and fixed before the prereg commit.
- **Rounds 1 and 2 rebuild too.** Every round's packet, uncounted rounds 1 and 2 included, rebuilds identically from
  its target. An `a4.json` rebuild takes about 5.5 minutes, a packet about 3 seconds.
- **The lead's M3 records carry stale generator hashes.** At `a3666ec5`, re-running one M3 law rewrites its record's
  `generator_sha256` (`cd3aff88` to `ca012339`), so the committed M3 records' hashes predate the lead's code. All 204
  M3 traces are stale too, on `config/holon.json`. I101 neither causes nor changes either one: its subset runs touch
  only scratch worktrees, and no closure file moves. No CI job runs G1 on M3, which would see it.
