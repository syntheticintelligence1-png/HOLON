## Surprises

1. **P1's entry index.**
   - The codec layer orders a function's encoder entries by their cells' JSON (`analyses.encoders`).
   - Under 0.2, the BaseFee-set entry's 32 `["unknown"]` cells sorted after the nil entry's zeros. Under 0.3 its
     `["byte", ...]` cells sort first. The set entry is now entry 0.
   - I did not change the order to fit the prediction. P1's test fails on that one assertion, and P1 counts as missed.
   - The laws do not move: `_0` and `_1` are both PROVED. Only which entry each one names differs from the prereg's
     description.
2. **G9's "fewest loop iterations" is zero, but zero has no replay.**
   - An empty batch's legacy hash is keccak(""), which is not an on-chain data hash either. The law fails there too.
   - G10's replay needs the Solidity inputs the witness names, and an empty batch has no last block number.
   - The decider therefore takes the fewest iterations whose replay has a correspondence: one.
3. **encoding/binary needed no new primitive.** I67's codec layer already models PutUint and Uint as cells and
   `be_uint` reads. 0.3 adds FillBytes only. The BUILD_PLAN row named both.
4. **Bend limits shaped O6's model.**
   - A function-typed binder cannot be reused, since `+` needs Data. The Solidity loop's answers are therefore a list
     `hc` with the premise |hc| = 32 · count.
   - The count's own two byte cells, and lastBlockNumber's eight, are free U32 variables. That makes the universal
     stronger, so the refutation is stronger.
   - `Nat.mul` reduces only with the symbolic factor first. `Nat.mul(32n, 2n+k)` sticks, while `Nat.mul(2n+k, 32n)`
     reduces.
5. **BendTT** rejects O5's counter-law with its TypeScript/kernel mismatch message, as it rejected large terms in I92.
   The verdict is recorded, not a status. D3's proofs and O6's counter-law check under both kernels.
6. **The Solidity facts already held O6's preimage.** commitBatch's store at BatchHeaderCodecV0.sol:175 holds the full
   term `keccak256(slice(mem(...), 0, 10 + 32 numL1Messages))`, so no new Solidity extraction was needed. The internal
   function's name is not in the facts: the replay reads it from the pinned source at the frame's call site.

## Questions for the human

1. **O6's intent.**
   - The legacy `DataHash` serves batches sealed when `isBatchUpgraded` is false.
   - At the pinned Rollup, every version's data hash is the new formula: `_commitBatch` hashes lastBlockNumber,
     numL1Messages and the hashes.
   - So a legacy-path batch's local header never matches the chain.
   - Is the legacy hash meant for replaying historical batches against an older Rollup? If so, should a later key
     state O6 over that contract?
2. **O5's severity.**
   - The estimator says "fits" for a payload whose compressed form needs a second blob.
   - `handleBatchSealing` then fails with "compressed batch size exceeds capacity", unless a replay raises the blob cap.
   - Is a sealing failure the severity you intend for O5?
3. **The halves left out.** Should later keys take them?
   - O5's "omits contexts" half: a batch straddling the upgrade (I91 Q6).
   - D3's decode half: node/types' DecodeBlockContext and the BaseFee equality helper (I91 Q7).
4. **HypZ.** `go_branch` takes HypZ_len only, because the estimators never decode. Do you want HypZ as a premise too,
   with its non-vacuity instance?
