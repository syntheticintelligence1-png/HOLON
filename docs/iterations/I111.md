## What was built

### (1) The per-document `holon types` fallback (Q77): `holon.sorts.opaque`

**Opt-in only.** A typed-sorts sidecar names `"types_fallback": "opaque"` (the only value; any other is refused when
the sidecar loads). Without the key, nothing changes: `holon types` refuses the milestone on an ill-sorted term
(N2: exit 2, nothing written). No Morph sidecar names the key (P6). The composed driver copies the key from the
protocol into every typed sidecar it generates.

**"Opaque", as the prereg defines it (O1-O7, before any build commit).** Under the key, `holon types` types each
document on its own, in sorted order. A document whose typed model generation raises the ill-sorted error is
opaque:
- **O1, a recorded miss:** one entry of `gen/<M>/sorts/opaque.json`, `{document, sha256, model, term, reason}`. `term`
  is the action and the operation (the error's first clause), and `reason` is the error's whole text with its source
  span. `types.json` gains an `opaque` list. The composed row records `types_opaque`
  `{documents, typed, opaque, misses: [{document, term}]}`, a stage reason before any decision (Q72).
- **O2, its state:** it has no typed model, so no state variable of it exists in any model, and nothing constrains it.
- **O3, its actions:** none is modelled, and no law of any rule is derived over it. Every claim over it is UNKNOWN,
  counted at the document.
- **O4, what other documents may assume about it:** nothing new. Every typed model is one document's. Another
  contract is reached only through an external call, whose answer is a free value (A-env) whether or not the callee
  is typed. So a typed document's model, laws and verdicts do not depend on an opaque document being in the
  milestone. The one exception is the milestone-wide assignment hash in the model's header comment, and so its
  `model_sha256`.
- **O5:** every stage after types reads the typed documents only: model, disch, derive and run.
  `typed_sidecar.Sidecar.documents` leaves out the documents `opaque.json` lists, under the key only. The sort pass
  and `holon types` read `Sidecar.all_documents`.
- **O6:** a taint violation still refuses the milestone, and an unreadable input still exits 1.
- **O7:** when every document is opaque, `types.json` has no model and `holon types` exits 0.

Three consumers read documents other than through the typed sidecar's list. Each now skips the opaque ones, under
the key only:
- DISCH's sidecar has its own document list. `holon.analysis.closure.Sidecar.analyses` skips a document that its
  typing sidecar's `holon types` made opaque.
- SYM reads the assignment's models, which cover every document. Its producer drops an opaque document's model.
- Derive's DISCH producer re-runs the same analyses, so it agrees with `holon disch`.

### (2) The torsor-role search (Q78): decomposition D1

The search decides, for one affine component, whether the classes' role domains (subsets of {P, G}) admit an
assignment satisfying every ternary table. With P = 1 and G = 0, each table is `out = lhs + rhs` (or
`lhs = rhs + out`) with no carry. That is a 1-in-3-type relation, so with seeds the problem is NP-complete, and every
exact strategy is exponential in the worst case. The old strategy propagates (generalized arc consistency), then
branches on the least open variable, chronologically. Suppose the leftover network has independent parts. A part
that fails is then re-discovered under every combination of choices in the parts sorted before it, so the search
thrashes exponentially.

**D1:** after each propagation, the constraints that still hold a variable with more than one role are grouped by
the connected components of those variables. A constraint whose variables are all decided is satisfied, because
propagation left it a supporting row, and it drops out. With two or more parts, the network is satisfiable iff every
part is: each part is searched on its own, in order of its least open variable, stopping at the first that fails.
With one part, the old branching is unchanged. This is an evaluation strategy only. `_search` returns the same
boolean on every input, so the satisfiable verdict, every role set, role pair and difference sort, and so every sort
output, are the same. It never changes which roles are admissible. `holon.sorts.solve.DECOMPOSE = False` is the old
strategy, for the identity test only.

**No new tier.** The sort budget's tier stays I110's 5,000,000, and the units keep I110's definition. D1's own scan
of a node's constraints is not metered. It is one pass over constraints that the same node's propagation reads at
least three table rows of each, so time stays within a constant factor of the metered work.

**The planted blow-up** (`tools/i111_search_fixture.py`, `tests_m6/fixtures/i111/search/blowup.json`) is built from the
search's semantics. It takes nothing from the spent target except I110's report that the time goes to `_search`.
The component is seeded Time through t. It has n gadgets (a_i, b_i, t) under +, two solutions each and independent
given t, sorted before an odd cycle (x, y, t), (y, w, t), (x, w, r). Arc consistency leaves the cycle open, but it
admits r only as G. Asking whether r can be P makes the old search walk 2^n gadget combinations.

## Soundness

**Opacity only removes constraints. It never adds one.**
- An opaque document contributes nothing to the typed model: no model, no state variable, no action, no law (O2,
  O3). Nothing over it can be PROVED or REFUTED, because nothing over it is derived. Its claims are UNKNOWN, and the
  miss is recorded with its term and reason, so it is never silent.
- A typed document's model is generated from its own document, the frozen assignment and the sidecar's seeds and
  binding. It does not read another document's model. Another contract appears only as an external call, whose
  answer is A-env free in every model, typed callee or not. So an opaque document's presence changes no typed
  model's constraints. The one exception is the assignment hash in a comment, which is not a constraint. P3 checks
  this byte for byte on the planted cross-document milestone, and P4 checks the verdicts.
- The sort assignment is the sort pass's over all documents, as without the fallback. The fallback never changes a
  sort, so no refinement is gained or lost by any typed document.
- So the laws decided under the fallback are a subset of the laws decided over the same milestone without the
  opaque document, each with the same verdict.
- REFUTED still needs its replay, as before: the composed route's replay and filter stages are route A's, unchanged.
- Without the opt-in, every path is the old one: `Sidecar.documents` filters only under the key, and `holon types`
  catches the ill-sorted error only under the key.

**Q62 interaction.** Route C's diagram and evidence read the transitions documents directly. So the opaque document
appears in `gen/<M>/evidence.json` atoms and in DERIVATION.json's provenance lists: the inputs read and the codec
layer's `uncovered` list. It appears in no law, record or statement (P3's check, amended before any measured run).
Evidence atoms are record annotations, not premises, so they can only annotate a typed law.

**The search rewrite changes no answer.** D1 relies on one fact: a propagated network whose open variables split
into parts that share no constraint is satisfiable exactly when each part is. Any solution of the whole restricts to
a solution of each part. Conversely, solutions of the parts combine, because no constraint spans two parts and every
dropped constraint is already satisfied by the decided values. So `_search` computes the same function, and P12
shows it byte for byte on every document where the old search finishes.

**The budget.** The tier is unchanged, and the new strategy's units never exceed the old's on the identity set (P13).
So no document under the tier with the old code moves over it. A document the old code put over the tier may now fall
under it. Its sort output is then the full pass's, and identity with the old code is claimed only where the old
code finished (P14).
