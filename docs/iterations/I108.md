**(a) S1-S3.** holon-sort-types/0.4 is 0.3 plus three rules for the operators the IR defines for intN
(`holon/frontends/solidity/transitions.py`, two's-complement words; I105's Go frontend emits the same):
- S1: `["s<"|"s<="|"s>"|"s>=", a, b]` is a comparison event of `a` and `b`, as the unsigned operator is. A sort is
  a dimension (what a word measures); two's complement changes the order of the words, not what they measure.
- S2: `["sext", bits, t]` is `t`'s value: `t` flows into a fresh result. Sign extension reads the same quantity as a
  signed integer.
- S3: `["sdiv"|"smod"|"sar", a, b]` is an opaque fresh variable with its operands walked, exactly as `/`, `%` and `>>`
  are. No debt.

The typed model compiles S1 as the unsigned order of the words with the sign bit flipped,
`w_lt(w_xor(a, 2^255), w_xor(b, 2^255))` (the map x ↦ x xor 2^255 is the order isomorphism from the signed to the
unsigned reading of a 256-bit word), and `sext` as `((t & (2^bits - 1)) xor m) - m` with `m = 2^(bits-1)`, mod 2^256.
Both formulas were checked against the IR's own constant folding (`transitions.fold`: `_sgn`, `_sext`) on 20,000 random
words and widths. `sdiv`, `smod` and `sar` stay outside the model's language (a types refusal), so they never yield a
law. The model's prelude is untouched: the new code is inline expressions, generated only where a document holds one of
these heads.

**(c) Layout** (`holon-layout/0.1`, the protocol's `layout` key):
- L1: a unit's Foundry project is the nearest `foundry.toml` at or above it. Its remappings are `[profile.default]`
  remappings, then `remappings.txt`, keeping the first of each (context, prefix), with targets and contexts rewritten
  relative to the checkout (the frontend's solc base path). Nothing is auto-detected from `lib/`.
- L2: forge's base path is the project root, so a non-relative import resolves against the project. For each top-level
  directory D of the project that no L1 remapping has as its prefix, the context-scoped remapping
  `<project>/:D/=<project>/D/` is added. It applies only to units of that project. This is the one place the layout
  writes a remapping the files do not list; it restates forge's documented resolution rule, and it is disclosed here
  and in the protocol (Questions, 2).
- L3: every gitlink of the pinned tree that `.gitmodules` (read at that commit) names is a detached worktree of its
  clone at exactly the gitlinked commit, which must be reachable from a branch or tag (nothing fetched by sha). The
  clone rule's exclusions apply: the corpus protocol's `excluded_repos`, a URL that is not a GitHub repository, and any
  repository named in `spec/M6/predictions/I106.json` (not present on this branch; the check reads it when it exists).
  Nested submodules recurse to depth 3. Every submodule is recorded in the entry's `sidecars/layout.json` (the holon
  runner) or row `submodules` (the go-machines runner): path, URL, commit, status, reason.

The Solidity frontend is not changed: the remappings go into the sidecar's `compiler.settings.remappings`, which the
frontend already passes to solc's standard JSON.

**(d) SYM per model.** `holon.sym.typed_models` lists every model of the milestone's assignment. The SYM producer
derives each model's elements. A law's ref is computed from the model whose facts the law names. Two models whose
elements give the same law id are refused, never merged. The SYM runner (`holon/symd/run.py`) was already per
document.

**(e) Nil maps.** Under the Go machine config's `machines.nil_maps: "unknown"`:
- every element write into a Go map field (a KV store is not a Go map) is `nil_map` debt;
- the typed model refuses a Go document that carries any such debt, so every law over that machine is UNKNOWN.

Without the key nothing changes: I105's documents, demo and tests are as they were. The I108 protocol sets the key
for the go-machines run.

## Soundness

1. **S1-S3 add no unsound inference.** The sort pass proves nothing itself; its output is candidate structure that the
   model generator compiles and Bend decides (I103's argument 2). S1 adds the constraint an unsigned comparison adds,
   and the sort relation is dimensional, independent of signedness. S2 is a flow: the value is the same quantity. S3
   adds nothing. A sort inferred wrongly could at worst give an ill-typed candidate, which the typed model refuses or
   Bend rejects. It never yields an accepted false proof.
2. **The model's signed operators are the IR's.** Both formulas are exact (above). A law PROVED over a model with
   them is proved over the IR's semantics. `sdiv`/`smod`/`sar` are refused, never approximated.
3. **DISCH's sign analysis (D9) has no signed rule, and gets none.** `holon.analysis.closure.sign` returns `?` for
   `s<`. A signed order is not monotone in an unsigned increase: crossing 2^255 flips it. So `?` is the sound answer.
   This is why the fixture's Acct derives no DISCH law (P1's miss).
4. **Remappings and submodules only add files the project states.** A unit solc reads through them comes from the
   pinned commit of a gitlinked repository, and the frontend still checks the checkout is clean. A wrong or missing
   remapping fails the compile (an extraction miss), and a miss is never a law.
5. **SYM per model is SYM's own statement, once per component.** Each law names its model's document, its basis is
   that model's elements, and its runner was already per document. No element crosses models. Duplicate ids are
   refused.
6. **Nil maps can only make laws UNKNOWN.** A document whose step may write a nil map is not compiled at all. Without
   the opt-in, I105's behaviour, and its soundness gap (Q60), are unchanged. That gap is disclosed below.
7. **REFUTED still needs its replay.** Nothing here touches the refuter or the replay. The smoke run stops after
   derive (`stop_after`), so it records no verdict at all: no PROVED, no REFUTED, no witness (Q56).

## Surprises

1. **I105's regression R1 fails on the merged branch, and not because of I108.** I105 pins the sha256 of every file
   of `holon/frontends/solidity/` and `holon/frontends/go/`. I103 changed five of them (solc selection by pragma, the
   go toolchain rule). So the merge of #170 and #172 fails I105-R1 on those five files. I108 changes none of them: the
   diff against I103's branch is empty. The lead lands both; the pins need the human (Questions, 1).
2. **The fixture's signed machine derives no law** (P1's miss). Sorts through derive all pass on Acct, but DISCH's
   blocked conditions over a signed comparison have sign `?` (Soundness, 3). Acct has no other guard over a writable
   flag. The prediction expected a DISCH law; the claim was wrong about DISCH, not about the signed rules.
3. **One prereg test was defective** (amended, `spec/M6/amendments/I108.jsonl`, before any measured run). It built its
   excluded URL as `https://github.com/` + an excluded_repos pattern, but the patterns already carry the host, so no
   implementation could pass it.
4. **Rule L1 missed forge's trailing-slash normalization** (P6). The test fixture's remappings all had trailing
   slashes. Optimism's do not.
5. **The Go machine frontend has no toolchain rule.** I103's go-directive selection lives in the codec frontend. The
   Go machine frontend always runs 1.24.7, so nitro's go 1.25 modules are refused there (c07, c12, and c01 in run 2).
6. **Past sorts, the Go documents meet new types gaps** (P9's table), not SP_b or nil maps first: method-call arity
   with the receiver, `len` of a word, whole-string writes.
7. **Disk.** The go-machines run copies a whole checkout for a generated `go.work`. With nitro's submodules (go-ethereum
   with its test fixtures), four parallel jobs ran out of the session's disk allowance: c01 and c08 in run 1. Both were
   re-run alone in run 2.
8. **c02's derive passes and gives nothing.** Its logic contracts are over the term-size budget.
