# I29: rule NAT over I28's versioned machine. 3 of 3 predictions held

I29 builds rule NAT (whitepaper §5.3) over I28's versioned machine of the Rollup's deployed path, V3 to V11.
- **Naturality (b):** a square per operation that reads an in-flight type at the new version and exists at the old one.
- **Composition (c):** a square per ordered pair of the path's initializers: the early one before the late one's migration, or after it.
- **Native equivalence (a):** a generated gap record per (in-flight type, reader). The machine defines no native state for those in-flight objects, so it states nothing.

All squares share one claim. From a reachable state, compare "migrate, then op at b" with "op at a, then migrate". They must end in the same version and the same storage (every slot either storage list holds), with the same success of the op and of the migration.

The key is `iterations.I29` in `spec/M3/predictions.json`. The contract is the docstring of `tests_m3/test_nat.py` (N1-N10, the own-commit rule). The prereg commit C_K is `1cc8e13d`, pushed before any build code. Before C_K, nothing about NAT ran except the instrument's basis over I28's outputs (disclosed in `thresholds.disclosure`). So P1-P3 all count.

## Surprises
- **Two naturality laws share one square.** proveState across V10->V11 reads both in-flight types, and the claim compares whole storage, so the two laws have the same claim function. Only their basis element tells them apart (the square ref hashes each law's own element). This follows from N3/N5 as preregistered.
- **The UNKNOWN has two causes, not one** (raised by I83, PR #57). N7's search never proposes a commit: its candidates are the migrations and the deployment record's calls, which hold no commit. And max_trace 10 leaves only two steps beyond the shortest trace to V10. So the three squares would stay UNKNOWN even with I28's model debt paid, yet the records' bound names only the debt. A search that can reach an in-flight object needs a commit candidate generator (I83 builds one for the versioned machine) and a larger budget. Both belong to a later key.
- **The recatalog helper was too slow here, so its entries were built another way.** `holon.statement_diff recatalog` re-checks every earlier binding_change line's equivalence proofs in both kernels while it scans the log, which took more than an hour here.
  - The catalog_rederivation lines were therefore built with the same entry construction, restricted to the working tree's registry changes (and, after I71, to the changes against the lead). This was done by scratch scripts and is disclosed here.
  - Each line was appended by `append` only after `check_entry` accepted it. All were accepted.
- **Git's history simplification left catalog lines untied, so this branch replaces PR #51.**
  - `holon.statement_diff.registry_changes` walks `git log -- laws/M3/REGISTRY.json` with git's default history simplification.
  - The first I71 merge (36665870) kept this side's REGISTRY.json, so it was TREESAME to this side and git pruned the lead's side. I71's 136 lines (1.6 -> 1.7) and this key's 137 (1.7 -> 1.8) then counted as untied in F39's tests, although G2's coverage passed.
  - The fix: a new branch from `a7630b54` whose I71 merge (`88c9a586`) carries the re-derived 1.8 registry, so it differs from both parents and git walks both sides. Only the cancel law's line (1.7 -> 1.8, `db45d03c`) was added. The CI re-make's records apply unchanged.
- **The first M3 re-make was cancelled.** Run 41013434887 was cut off by the lead's I71 ordering, and its DISCH job hit the deadline after 10 of 35 laws. Nothing from it was committed. The final re-make splits DISCH into 7 jobs and the typed laws into 3.
- **Other keys' files fail the exhaustive target-agnostic test.** tests_m2.test_target_agnostic_exhaustive flags holon/blind.py, holon/derivation/product.py and holon/report.py (I82 and I85, fixed on the lead by PR #62) and holon/mutate/* (base). None of I29's files is flagged.
