# I102: holon audit regress compares each commit with its own parents. It no longer reports changes no commit made, and no longer leaves out ones commits did make

**The findings.**
- **F-M3-07** (M3 round 2, medium by the lead's triage; the auditor rated it low).
- **F-M3-30** (round 7), its duplicate, which adds the second direction.

`holon/audit/regress.py` `hash_changes` walked each law file's path-limited `git log --topo-order --reverse A..B --
<file>` and compared each version with the previous one in that list. On branchy history that one is often another
branch's commit, which gives two failures:
- **Phantom changes.** The tool reported changes no commit made: 680 uncovered on round 2's range, and 408 on
  `fe1f88f2..ef39bed5`. Against the commits' real parents, none of these is uncovered.
- **Hidden changes.** The per-file log never visits a branch's commit whose file a merge took from its first parent.
  So the tool left out changes commits did make: 224 on `fe1f88f2..ef39bed5`, by round 7's `hidden_check.py`.

No status moved for either: the omitted changes all happen to be covered. But A3's covered/uncovered verdict could not
be relied on over branchy history, and A3 is what an auditor reads.

## The fix

`hash_changes` walks the commits of A..B that touch `laws/` (`git rev-list A..B -- laws/`), with every merge of A..B.
It compares each law file at a commit C with C's own parents (`git rev-parse C^@`):
- **What counts as a change.** A file changes at C when its version there (its statement hash, or absent) is none of
  its parents' versions.
  - A file that no parent holds is an addition, which `additions` reports.
  - A merge that takes one parent's version introduces nothing.
  - A merge that regenerates a file introduces a change against every parent.
- **What each change names.** The parent it is measured against (`parent`, the first parent of C that holds the file),
  with `old` the hash there and `covered_by` judged on that edge. A merge whose other parents hold the file under other
  hashes lists each such edge in `other_parents`, with its own `covered_by`.
- **The cost.** Blobs are compared before anything is hashed, as round 7's checker does. Only a file whose blob at C is
  none of its parents' blobs is hashed, at C and at each parent holding it, and the hashes are cached per
  (commit, file).

No other report key changes. The text output names each change's parent. No generator closure module changes (B7), so
no record's `generator_sha256` moves.

## Surprises

- **B3 and B4 over-read the findings, and were amended.** As preregistered, they asserted that the fixed tool reports
  nothing at the merge `41c7e34` (and `ecbb695` for round 2). The findings say those merges equal their first parent,
  but they say it of the 136 laws they name. `41c7e34` also makes 8 real changes. Its first parent lacks those laws and
  its second holds them under statement-hash scheme 1; the merge migrated each to scheme 2, and its `hash_migration`
  line covers it (line 1148 for `L_disch_self_Rollup_challengeState_489_493`). The two `test_defect` lines in
  `spec/M3/amendments/I102.jsonl` came before the edits. The amended checks assert that none of the named laws is
  reported at those merges, and that every change there is covered. The contract docstring and the key are unchanged.
- **A3's file scope left out the law sets in subdirectories.** Five of round 7's 224 hidden changes are in
  `laws/M3/derivation/`: the derivation law set, at the hash-scheme migration `a7d372a`. A3's law-file pattern,
  `laws/<M>/L*.json`, never matched them, before or after the parent fix. `hash_changes` now also reads
  `laws/<M>/<set>/L*.json`: the derivation law set and M5's bounded games, which `law_hash` hashes the same way. That
  is what makes round 7's checker find 0 unreported changes. `additions`, `laws` and `transitions` keep
  `laws/<M>/L*.json`, because those sets' records live elsewhere.
- **A3 cannot see a change the facts drive.** A3 walks only the commits that change a law file. The six M2
  `reextraction` lines record statement changes that the re-extracted facts drove while the law files stayed the
  same, so A3 sees none of them, before or after I102. That is why P3 holds vacuously. The registry tie (G2,
  `holon.statement_diff.registry_changes`) is the view that covers them.
