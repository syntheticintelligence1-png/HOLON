# I63 (= I28a): deployment history from the code, cross-checked on chain. 10 of the proxy's 12 upgrades match a tagged version; mainnet ran hardhat's runs-10000 builds until the cutover (P2 missed); one implementation carried LAYER_2_CHAIN_ID = 1 for six and a half months

I63 is the history half of BUILD_PLAN I28, under its own key (`prompts/I63_history.md`). It builds every tag of the target repository that holds `Rollup.sol` (25 tags, plus the pinned head), groups the builds into code versions, and diffs their storage layouts into MIG edges. It then reads the proxy's 12 upgrades on chain and matches each deployed implementation against the builds. It states no law and changes no catalog. The laws half keeps the key I28.

- **History:** 26 refs build into 11 code versions with 10 MIG edges, as the prereg's basis computed. Two edges are incompatible. The cutover's in-flight set holds the reinterpreted state that I28 inherits (Finding 5).
- **On chain:** all 12 receipts hash to the receipt hashes I59 committed on 2026-10-13.
  - The build review read all 12 implementations' code again from two RPC providers other than the sidecar's, and every sha256 agrees with the snapshot. No prediction is UNKNOWN.
  - 10 upgrades match exactly one version. Two match none:
    - the proxy's creation over a placeholder, as predicted;
    - one launch-week upgrade (block 21007191). The build review identified it as an untagged variant of v0.4.0 (Finding 3).
- **Compiler settings:** every matched upgrade before the cutover matches the `hardhat` configuration (optimizer runs 10000). Only the cutover (V11, I23's implementation) was built with runs 200. P2 predicted runs 200 throughout, and missed.
- **A misconfigured immutable** (Finding 1).
  - The implementation deployed at block 22465639 (2025-05-12) has `LAYER_2_CHAIN_ID = 1`. Every other real implementation has 2818, Morph's chain id. The same code version was redeployed with 2818 at block 23874746 (2025-11-25).
  - In that code version, `LAYER_2_CHAIN_ID` is the first field of the defender's ZK proof public input (`_verifyProof`, reached only from `proveState`).
  - I59's index holds one ChallengeState of the proxy inside that window, at block 23846280, four days before the redeploy.
  - The build review confirmed the value independently, by calling `LAYER_2_CHAIN_ID()` on two other providers.
- **Predictions:** 4 of 5 held (P1, P3, P4, P5). P2 missed.

## Findings

1. **LAYER_2_CHAIN_ID = 1 in the implementation live from block 22465639 to 23874746 (2025-05-12 to 2025-11-25).**
   - **The committed code.** The words of `0x9c79e8f5…` at the V6 hardhat build's two immutable ranges ([1516, 32] and [14889, 32]) both hold 1. The redeploy at 23874746 (`0xdf0749e6…`) holds 2818 there, and the two codes differ only in the last two bytes of those words. `LAYER_2_CHAIN_ID` is the contract's only immutable.
   - **The build review's independent check.** `eth_call` of `LAYER_2_CHAIN_ID()` (selector `0x5f77cf1d`) on `ethereum-rpc.publicnode.com` and `eth.drpc.org` returns 1 for `0x9c79e8f5…`, and 2818 for `0xdf0749e6…`, `0x213ce22b…` and every other real implementation. The placeholder reverts.
   - **What it affects.** In V6 (`v0.4.3`..`v0.4.9`), `LAYER_2_CHAIN_ID` is the first field packed into `_publicInputHash` in `_verifyProof`. That hash goes to `verifier.verifyAggregateProof`. `_verifyProof` runs only from `proveState`, on its defender branch, before a challenge times out. commitBatch, finalizeBatch and challengeState never read it. So for six and a half months, a defender's proof was checked against a public input that commits to chain id 1. What the verifier then accepts is not in the evidence.
   - **The challenge in the window.** I59's index holds 8 ChallengeState logs of the proxy. One, at block 23846280 (tx `0xe92cd210…`), falls inside the window, 28,466 blocks (about four days) before the redeploy. The next, at 23874907, comes 161 blocks after the redeploy.
   - **How that challenge ended is not in the repository.** I59 did not fetch ChallengeRes, Paused or Unpaused. The index and V6's code rule out two endings:
     - challengeState at 23874907 requires no open challenge and no pending revert request;
     - the index holds no RevertBatch log over the whole window.

     So the challenge did not end by a challenger win on timeout, nor by revertBatch. Two possibilities remain: a defender proof the verifier accepted (before or after the redeploy), or setPause(true) followed by setPause(false).

   This is an observation of deployed state, not a law. HOLON's models take the chain id from the binding, and no I63 rule reads immutables (Finding 4). It goes to the findings lane (Q60).
2. **Hardhat builds on mainnet.**
   - Nine implementations (V3-V10) are the `hardhat` configuration's builds of their tags: optimizer runs 10000, cancun, bytecodeHash none. Only V11 is a runs-200 build.
   - The build review rebuilt v0.4.3 itself and confirmed it: runs 10000 matches both V6 deployments, runs 200 matches neither.
   - I23's Surprise 1 (runs 200) holds for the cutover alone. A replay or model of the pre-cutover versions should build them with the hardhat configuration.
3. **Block 21007191: an untagged launch build, explained.**
   - **The match.** Its implementation (`0x073403e1…`, 17,900 bytes) matches no version under any configuration. The build review reproduced it byte for byte: v0.4.0's `Rollup.sol` with line 181 deleted, `require(finalizedStateRoots[0] == bytes32(0), "genesis batch imported");`, built under the hardhat configuration. That line is the one-time guard of `importGenesisBatch` (onlyOwner).
   - **How it fits I59's record.** I59 records two `importGenesisBatch` calls, at blocks 20999915 and 21007528, one on either side of this upgrade. So the owner re-imported the genesis batch through a build without the guard. This explains I59's Surprise 6: two genesis imports, with different batch hashes, at those two blocks. The guard came back with V4 at block 21283676, 39 days later.
   - **No commit holds it.** The lead built every commit touching the rollup or the libraries between 2024-10-01 and 2024-11-27, under all three configurations, and found no match. The review found that no reachable commit removes the guard.
   - **Status.** It stays coverage debt by the rules (H8). It bears on O9, the genesis-import prediction of the laws half (I28).
4. **The redeploy of V6 is invisible to the timeline.** H2's identity masks immutables by design, so the timeline shows block 23874746 as V6 -> V6, consistent. Keying a deployment by (version, immutable words) would make it visible. That is a contract change, left to I28.
5. **The cutover's in-flight state** (from the basis, V10 -> V11):
   - `Rollup.batchDataStore` is retyped: BatchData's fourth member, `signedSequencersBitmap` (uint256), becomes `submitter` (address);
   - `Rollup.submitterContract` reinterprets `Rollup.l1StakingContract`'s slot.

   `initialize4` ran in the cutover's own transaction, so slot 151 was overwritten atomically. Every batch committed before the cutover still reads its bitmap's low 160 bits as `submitter`. I28's in-flight sets start here.
