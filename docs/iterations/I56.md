### Payoff facts and V9 (the lead's condition 1)

`python -m holon games flows` writes `gen/M5/games/value_flows.json`. It is generated from the seven deployment documents only (Rollup, the bundle's five members and the router), each pinned by sha256 in the sidecar.
- **Constructs:**
  - VM1: payable;
  - VM2: a call with non-zero value;
  - VM3: a write to a claim ledger;
  - VM4: a value-moving call into another member. The callee is matched by the action's name and by the `<I>.sol` unit of the interface the call is typed by. This rule separates `Submitter.slash` from the legacy `L1Staking.slash`.
- **Claim ledgers:**
  - `Rollup.batchChallengeReward` and `Submitter.stakeOf`;
  - both are redeemable by their holder's own call, so both count as eth (G-A2).
- **Coverage, V9:** 23 of 23 value-moving actions have a complete entry listing each of their constructs (`results/M5/games/v9.json`). V9 therefore holds, and L6's decided threshold is judged rather than `not_judged`.
- **Independent check:** the instrument computes the value-moving set without `holon/games` (F1, F2).
- **Use:** the run evaluates payoffs from the document's entries only. A missing entry therefore changes payoffs, and V9 catches it (adversarial probe 2).

### Strategies as checked programs

There is one Bend module per game (`gen/M5/games/bend/<game>/`). `LAWS.bend` holds:
- the verdict law `l_game_<g>: {G.verdicts() == [...]}`;
- one `exs` strategy law per rational class, whose proof returns the strategy.

How each kind of game is checked:
- **Controls (complete games).** Bend computes every class's verdict by a fuelled depth-first search over every schedule of distinct actions inside the module (fuel = actions + 1). The universal half ("every triggering schedule is negative, or none triggers") therefore needs no list from the generator. `deep`'s rational strategy is found beyond the document's horizon field (lengths 3 > 2 and 4 > 3), and `recoup` is read at the schedule's end.
- **Targets (witness games).** Bend computes each class's legality and the classification of the witness's flows.

Bend prints ALL PROOFS CHECK on all 26 modules (14 control, 9 target, 3 econ), and BendTT (`--verdict`) checks all 26. In probes, tampered verdict vectors were refused.

## The adversarial phase

I ran it myself, without a subagent: probe scripts against the prereg before the freeze, then against the build and HOLON's own records.

### Before the freeze (folded into the prereg)

1. **The blind-engine test left the horizon field intact.** An engine that read `horizon` would fail `deep` but still pass C2. C2 now sets `horizon` to 1 in the blind copy.
2. **N3's REFUTED/UNKNOWN boundary was ambiguous.** An undetermined payoff would have been "refuted" by the negation of a classification label. The key now says REFUTED only when no classification the claim reads is undetermined (`n3_status`).
3. **The value-flow document could be decorative.** Payoffs computed from the documents directly would make V9 a report, not a constraint. The key now requires the engine to evaluate payoffs from the document's entries only.
4. **B1 checked that Bend accepts, not what it accepts.** Each record's evidence law must now state that record's class verdict vector, in class order.
5. **VM4 was ambiguous.** `slash` exists in both `L1Staking` and `Submitter`. The callee is now matched by name and by the interface's `<I>.sol` extraction unit.

### On the build (not folded: they are measurements)

1. **Tampered verdicts.** Flipping a control's or a target's verdict vector in LAWS.bend (deep's class to IrrB, costly's to Rat, a target's Unk to Rat) gives SOME PROOFS FAIL every time.
2. **Empty value flows, I54's G1 in N3 form.** Against an empty document, N3 reads the recommitter's payoff as **nonneg** (and both continuation callers' as nonneg): a rational recommitter would *recommit*. V9 drops to 0 of 23 and catches it. Without V9 the N3 law would have come out REFUTED on a document that models no value. L6's decided count does not move in this probe (still 0), because legality, not payoff, is what keeps the target classes UNKNOWN.
3. **A horizon-bound engine.** One that reads the documents' horizon field misses `deep` on both instances (strategy lengths 3 > 2 and 4 > 3): false_irrational catches it.
4. **Constant-verdict and record-forging engines.** T1 recomputes every target record's classes and payoffs from the instrument, and C1 does the same for every control. B1 requires the evidence law to be present in a module Bend accepts. A constant "rational" engine fails T1 on all 9 target records.
5. **Unsound resolution would raise the headline.** Treating an unresolved party as "not a deviator" (the unsound direction of G-R3) is the cheap way to raise decided and N3. The frozen rule forbids it, and the probe in Surprise 1 is labelled diagnostic, not a result.

## Surprises

1. **N3 is UNKNOWN, not PROVED (P1 and P2 missed).**
   - *The rule that blocks it.* Under G-R3, an unresolved party is possibly a deviator: a credit becomes a credited atom, a debit a debited atom.
   - *Where it bites.* Two flows on the witness's run have parties the pre-state cannot resolve:
     - revertBatch's `batchChallengeReward[challenges[i].challenger]` write, whose key is loop-carried (Rollup.sol:444–467);
     - Submitter.slash's transfer to `rollupContract`, a word of the callee's storage that the run does not hold.
   - *The effect.* Each puts a credited atom and a debited atom on every address, so every payoff on the run is *undetermined*. Under the frozen rule `n3_status` that is UNKNOWN, and nothing was changed.
   - *A post-hoc diagnostic (not a result, not scored).* I read the deviators' own `batchChallengeReward` slots before and after each step. The recommitter's claim never moves, and the challenger is credited exactly its deposit (1) at proveState. So under an exact per-holder reading:
     - the recommitter's only movement is the Submitter stake debit, which is negative under P-bond, and refusing gives zero;
     - the challenger nets 0 and the chooser 0.
     That is N3 as the whitepaper states it.
   - *A proposal* for a later key, preregistered before it runs: VM3 evaluated at the deviators' own ledger entries, and a callee storage word resolved through the deployment binding.
2. **No untrusted class runs a target witness alone (P5 missed, 0 of 49).** The forecast assumed the link-domain witnesses (commitBatchWithProof and proveCommittedBatchState, both permissionless) would run, but they do not. Their records' own engines supplied environment answers (`IL1MessageQueue.getFirstUnfinalizedMessageEnqueueTime`) and immutables that the Rollup's deployment env lacks. Two definitional choices also exclude findings:
   - G-W3 concatenates UNDO's `t` after `x;y`, so it reverts. That revert is the UNDO finding.
   - G-R2 rejects any non-ok step, which excludes witnesses whose trigger is a revert, such as SORT realize's overflow panic at Rollup.sol:363.

   These are preregistered rules, so they stand. A later key could add a witness form for "the trigger is the last step's revert".
3. **Two of the three O35 laws carry little information.** commitBatchWithProof and commitState move no value at all: no construct, an empty asset vector. Their ∀k laws hold over an empty vector, and the content is the document's fact that they are not value-moving. Only commitBatch's law (payable, a VM1 flow priced at msg.value 0) exercises the induction over a real component.
4. **Two amendments.** The second came after the lead's merge (`f32c206b`): `test_r1` diffed the whole tree against the base, so the lead's merged M2/M3 changes read as I56's. It now checks the files of I56's own commits (first-parent, non-merge). Against the lead's head, the M0–M4 diff is empty. The first: `test_n3` (E1) required checker evidence even for an econ record it had just required to be UNKNOWN, which contradicts the key's B3. It now requires the evidence for a PROVED or REFUTED record and a reason for an UNKNOWN one. No status expectation changed, and P1 and P2 stay red.
5. **Unary Nats.** Bend's `Nat` is unary underneath, so the generator refuses a concrete amount above 65,535 (the game becomes UNKNOWN with that reason) instead of emitting an infeasible module. No game on this target hit the limit, because the witnesses move 0 or 1 wei. A target with real amounts would need a binary representation.
6. **Toolchain.** As in I54, the CI install script needed `zstd` installed first. `verify_toolchain.py` then printed PINS ALL PASS (13/13). The clone was shallow, and `git fetch --unshallow` was needed before the prereg audit could run.
7. **A test run before the prereg commit.** One run of the then-red contract tests, to confirm they were red, executed the instrument's target-game computation before the prereg commit. Its values were not printed or inspected. I disclose it as BUILD_PLAN §0.1's undetectable-local-run risk.

## Questions for the human

1. **N3's measurement rule.** Should the next key measure VM3 at the deviators' own ledger entries (exact, sound for D) instead of at the written key term? G-R3's conservative rule makes every payoff on a run undetermined as soon as one ledger write has a loop-carried key. Under the exact rule, the diagnostic above reads N3 as the whitepaper states it.
2. **Witness forms.** Should a later key add a form for findings whose trigger is the last step's revert (SORT realize, UNDO's `t`)? Should it also run each family's witness in the environment its own engine used (the link-domain answers and immutables) instead of the deployment env?
3. **Trusted flags.** The sidecar trusts every member's onlyOwner group and nothing else (G-C3). Is a challenger, which sits on a whitelist the owner maintains, untrusted for L6, as fixed here?
4. **L6's decided headline.** With single-deviator semantics (I54) and witness games, decided can only count findings whose witness one class runs alone. On M3 none qualifies. Should L6 also report the robust form, ∃σ ∀ schedules of the other classes ≤ H, which the plan's goal names and N3 needs?
