## Surprises

1. **The pay point is not robust** (P1). The plan expected both points PROVED in the §8.4 form. The pay strategy is
   two transactions, and a permissionless batch submission by anyone between them includes the submitter's message.
   Under two such events the cheapest delay-0 route costs three messages: the robust frontier is {(0, 19), (3, 0)}.
   The finding is relative to M1's machine and cost model, and to H = 2.
2. **(1000, 0) is not a point of commitBatch's profile** (R1). M1's prove point (L_disch_delay_prove) counted a batch
   committed by commitBatchWithProof, a different action whose guard bypasses the delay guard. Def 6.20's profile is of
   commitBatch's guard, so the outcomes are (1001, 0) and (1000, 19) and up (prove, then pay or wait, then commitBatch),
   all dominated. The frontier part of R1 holds.
3. **Two instrument bugs** (both amended before any comparison): the instrument matched the facts' principal label
   for equality, so `sendMessage` ("anyone (through the messenger; ...)") was never X's, and its table replay read a
   row's move through an alphabet its caller never sends.
4. **Bend's module tags.** A state built by one compiled module cannot be passed to another (`bend: ... has no tag
   HSt`), so the search compiles κ into the model's own namespace (`ob_kappa`; the model already has a `kappa`).
5. **A priority list suffices** for the wait point: the winning table has 1934 rows (673 off the plan), but they use
   19 distinct moves, and greedily playing them in a generic order wins every schedule.
6. **The contract's statuses.** C1 says a T32 law is PROVED or UNKNOWN; the checker's word gives REFUTED to the pay
   point (its counter-law checks), so `TestKernel` and P1's test disagree with the contract there, by design of
   AGENTS.md rule 6.
