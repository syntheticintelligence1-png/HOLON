# I105 (M6, generality): Go state machines in the Solidity frontend's IR

**Outcome in one line.** The Go frontend now emits transitions documents in the Solidity IR, for struct-field and
KV-store machines, with havoc for every write it cannot resolve. The typed pipeline (sorts → derive) runs unchanged on
Go-only machines and derives DISCH laws from one. On I51's 8 Go entries the counted run derives 0 laws: no entry
completes. The refusing stages are named below: three frontend crashes, which are fixed; then the sort pass on signed
terms (I103's ground); then the typed model.

## What was built

**`holon extract go_machines`** (`holon/frontends/go_machines/`, a new frontend module):
- It reads the codec frontend's holon-go-frontend/0.3 config and SSA dump (its own helpers, imported; nothing of
  `holon/frontends/go/` changes).
- It writes one holon-facts/0.3 transitions document per machine: `<stem>.<Type>.extracted.json`, with `contract`
  `<package>.<Type>`.
- **A machine** is a named struct type with exported methods declared in a document package. Its fields are the
  families, at slot = field index and offset 0, and its exported methods are the actions.
- **KV families.** A field on which an action calls Get/Has/Set/Delete over `[]byte` keys is a KV family: a mapping
  bytes → bytes. That covers a call directly on the field, or on a store an opaque call derives from it
  (`k.storeService.OpenKVStore(ctx)`).
  - A key built from a constant prefix plus arguments is a structural term, e.g.
    `["abi.encodePacked", ["str", "62616c2f"], ["param", "addr"]]`.
  - Get reads, Has compares the read with the empty value, Set writes, Delete writes 0, and the iterators read. All of
    this is assumption A-kv.
- **The walk** is path-sensitive and symbolic over SSA. It inlines in-package static calls to the config's
  inline_depth, and its terms are the Solidity IR's. Go's fixed-width arithmetic is exact: `trunc`/`sext`, the signed
  comparisons and divisions.
- **Guards.**
  - A path that returns a definitely non-nil error and has written nothing is a guard: `errors.New`, `fmt.Errorf`, or
    a package error variable whose only stores are of those.
  - So is a path that panics (outside a deferred `recover`) without writing.
  - An error that may be nil gives a guard `["||", ["!", K], ["==", err, 0]]`, with `err` free. Both behaviours stay.
  - A failing path that has written keeps its writes, because Go does not roll back.
- **The document** has the Solidity transitions document's keys, plus `debt` (what was not modelled) and `info`. `info`
  is the view the model reads in place of a compiler: the families' layout in storage-layout type ids, the actions'
  inputs, and the ABI signature of every function a call term names, with a selector from keccak256 of its name.
  Selector collisions are refused.
- **The schema.** It is checked against `spec/schemas/facts_0_3.schema.json`'s new `go_transitions` branch: additive,
  closed, a third `oneOf` branch. The Solidity branches are unchanged. `facts_version` stays holon-facts/0.3, because
  every consumer gates on it. The Go documents are told apart by `extraction.frontend` "go" and versioned by
  `extraction.frontend_version` holon-go-machines/0.1.

**Two consumer edits, Go documents only.** Each one checks `extraction.frontend == "go"` and leaves the Solidity path
untouched:
- `holon/machine.py` `toolchain_info`: a Go document's `info` is the model's compiler view. A Solidity document still
  compiles through its sidecar.
- `holon/sorts/model3.py` `t_unknown`: in a Go document, `["unknown", …]` is a havoc, so it compiles as an environment
  member of the step, keyed by the term (A-env: free). In a Solidity document it still raises, as before.

**`holon eval go-machines`** (`holon/eval/go_machines_run.py`) is the smoke driver. It runs I51's checkout, packages,
sources and config (`holon_run`'s own functions), then `extract go_machines`, then I51's five typed stages sorts, types,
model, disch and derive, with I51's generated sidecars. It writes `results/M6/I105/corpus.json`.

## Soundness: why havoc never drops a write

The claim: for every concrete run of an action from a state, the model holds a transition with the same final state
(and, for a guard, the same failure). The model may hold more. The argument:

1. **Paths cover runs.** Every run of a loop-free stretch follows one SSA path, and the path's condition holds on it.
   A loop is not iterated: the walk continues at every exit, with the loop's values unknown.
2. **Resolved writes are exact.** A store through the receiver pointer, a local alias of a field address (a symbolic
   memory tracks local cells), and a map update of a map read from a field all name their family and path. That
   includes a value receiver's copy: Go copies the struct, but the copy shares its maps. A value receiver's field
   assignment writes only the copy, which is no state write (planted: `Lose`, `Credit`).
3. **Unresolved writes taint.** A family is havocked at the end of the path, and every later read of it in the path is
   a fresh unknown, when it may be reached by any of:
   - a store through a pointer read from the state, through a global, or through any unresolved address (every family);
   - a store below a field, or a whole-receiver store;
   - an opaque call, goroutine or defer that is handed a state pointer, map, KV store or a closure over them;
   - a store, map update, KV write or reaching call inside a loop.

   An unknown term is free, so any concrete final value of a havocked family is one of the model's.
   - The roots of a call's arguments are found by definition chains. An operand of a reference type that is not
     resolved counts as reaching every family.
   - A goroutine's or defer's in-package body is scanned the same way as a loop.
4. **Guards remove only failing behaviours that change nothing.**
   - A guard is a path that wrote and havocked nothing, and that definitely fails: a non-nil error by the library's
     semantics, or a panic no deferred `recover` can stop.
   - Its concrete runs all fail with the state unchanged, which is exactly the model's revert.
   - A maybe-nil error keeps both outcomes through its free disjunct (planted: `Parse`).
   - A recovered panic is not a guard (planted: `Safe`).
5. **The path limit** (max_paths, 512) havocs every family and drops every guard. That only adds behaviours.

**Planted tests** (P2, and `TestGuardSoundness`, added after the prereg):
- an alias resolved exactly;
- `&a.Y` handed to a dynamic call (Y havocked);
- a write through a state pointer (every family havocked);
- writes in an argument-bounded loop (Arr and N havocked, K := 7 after it exact);
- a goroutine writing X (X havocked, Z := 2 exact);
- a maybe-nil error;
- a recovered panic.

**What the argument does not cover** (assumptions, written into every document):
- **A-implicit.** Go's implicit panics are not guards: nil dereference, index out of range, a nil map write, a failed
  type assertion. A run that panics there leaves the writes made before it, a partial commit. The IR cannot express
  that, so the model shows the path completing.
  - In particular, a struct's Go zero value has nil maps, so every map write from the zero state (DISCH's R0) panics in
    Go.
  - A law over such a step can be wrongly PROVED under this assumption. It is the main residual risk; see Questions.
- **A-reentrancy.** An opaque call writes only what its arguments reach. A call through an interface held in the
  state that holds a pointer back to the receiver is not seen.
- **A-kv.** A KV write that returns an error is modelled as written.
- **Selectors.** The 4-byte selectors of call terms are assumed collision-free (checked within a document).

GATES

## Surprises

1. **Two typed-pipeline stages are not total over the Solidity IR they are documented to read.** These are model
   limits, not Go ones:
   - `holon sorts` has no rule for the signed terms `s<`/`s>`/`sext`;
   - the structural typed model does not compile string- or bytes-keyed mappings (SP_b).

   Morph never needed either. Any Go integer comparison on `int64` and any Cosmos KV store meets them.
2. **The model refuses a havoc of a whole map.** That is sound, but it makes every loop over a map field unmodellable
   at `types`.
3. **Real Go code passes the receiver to helpers all the time.** So the honest over-approximation havocs most of the
   state on most paths (above).
4. **Generated protobuf types** (c18: x/group's 82 machines) count as machines by the preregistered definition, and
   they dominate the action count.

## Questions for the human

1. **A-implicit, the zero state and nil maps.** A Go struct's zero value has nil maps, so a map write from it panics. A
   DISCH law over R0 (the zero storage) can therefore be PROVED for a step that panics in Go. Should Go machines get
   their own R0 rule? One option: a machine is reached only through a constructor (a function of the package returning
   `*T` or `T`), and the zero state counts only when no such constructor exists.
2. **Who owns the two typed-pipeline gaps?** The signed-term sorts rules look like I103's "make the sort pass total";
   SP_b string/bytes keys in the structural mode would be a later model key. Until both land, no Cosmos KV machine can
   pass `types`.
