## O4 through derivation

The planted case `planted/blob_high_byte_late` sets byte 126976 of blob 0, the high byte of field element 3968, to 1. Through `ParseBatch`'s blob loop (`batch_info.go:114-120`), the real code panics in `common/batch.RetrieveBlobBytes` (`blob.go:49`) with "runtime error: index out of range [126976] with length 126976". The model panics at the same instruction with the same text.

**This is I67's O4 law `L_par_tot_batch_RetrieveBlobBytes`**, the totality law of the batch clone. I67 REFUTED it at the 4096-cell witness whose cell 3968 is 1, and its replay found the real clone panicking on the blob whose byte 126976 is 1. It is the same carrier value at the same site. I67's clone-pair laws (OPanic against OErr, and the domain law) are refuted at that same witness.

What I85 adds is the consumer: derivation calls the panicking clone (`common/batch`), not the fixed one (`common/blob`), and `ParseBatch` has no recover. So a blob of that shape, once its versioned hash is committed, panics the deriving node's `ParseBatch`. In I67's records the three REFUTED laws stay `go_only`, with the reason "node-level public path needs I39". This case is that public path at the consumer, on the real code. Stating it as a law over the product, and re-binning those records, is I39b's.

### The product machine's interface (for I39b)

`holon.derivation.product.Product(root, side)` gives:
- `.join`, the J1 rows;
- `.genesis` and `.state0`, the first parent and the deployment's storage;
- `.commit(state, parent, plan, blobs, k, prev_root)`, one Solidity commit step: status, the committed header bytes, the word written, the next state;
- `.batch_of(args, blobs)`, J2's derived batch;
- `.derive(batch, answers)`, the consumer model: status, error, panic, the receiver's dump and the exit site;
- `.trace(plan, blobs_of)`, a whole trace with the cycle.

A law can read:
- every header field the Solidity model committed;
- every `BatchInfo` field the derivation wrote: `batchIndex`, `version`, `root`, `withdrawalRoot`, `parentTotalL1MessagePopped`, `firstBlockNumber`, `lastBlockNumber`, `txNum`, and per block the number, timestamp, base fee, gas limit, `txsNum`, `l1MsgNum` and transaction encodings;
- the oracle's answers: the decoded transaction list, which against the blocks' dequeued counts is where O8's trailing transactions show.

For the I39 laws:
- O7: the commit's `lastBlockNumber` against the derivation's `lastBlockNumber`, and the next `firstBlockNumber` against it plus one;
- F11's L1 count: the header's `l1MessagePopped` against the sum of `l1MsgNum`;
- O8: decoded transactions against dequeued ones.

The machine is evaluator-level (Not done: a Bend product model; Q-I85-f).

## Surprises

1. **R4 against G4: my contract's own inconsistency.** The forbidden token `morph` and G4's prescribed key `"morph_commit"` cannot both hold in `holon/derivation/`. I fixed both clauses at the prereg, and the build exposed the clash (see "R4").
2. **The plan's `node/` dependency risk did not materialize, locally.** Every dependency is in the module cache. The frontend, the compressor, the oracle and the replay all ran with `GOPROXY=off`. No CI job runs `holon derivation`, so the Go side ran locally only. CI clones the checkout at the pin but keeps no Go module cache, and the replay runs offline. `refine --check` reproduces the model side from the recorded answers without Go.
3. **ssadump keys the empty interface by its printed name.** `any` is an alias whose underlying key is `any` itself. The interpreter first refused it ("underlying chain too long") on the first smoke run, before any record was written. A self-referencing alias is now read as the empty interface.
4. **go/ssa spills `ParseBatch`'s by-value batch parameter into a local.** The closure has no Field instruction, and the read set is a FieldAddr chain on that local. D5 named both forms, so P3 was unaffected.
5. **A build bug, found before any output:** the corpus builder refused a case with no blob but a payload (the random mutation `zero_blobs`). A case with no blob delivers no payload (C2); this was fixed before `corpus.json` was first written.
6. **Version 0 commits are accepted on L1 and never derivable at the head.** The Rollup's commit admits versions up to 2. A modern commit carries no calldata contexts, so `ParseBatch` counts zero blocks for a version 0 batch (`product/02/1`, `product/06/1`, `product/06/2`). P4 predicted it by reading, so it is not a surprise in outcome, but it is a cross-component domain mismatch that no law states yet (Q-I85-e).
7. **The blob decoder's error text shows I67's cosmetic defect through derivation:** "invalid blob, found non-zero high order byte 0 of field element 5" prints the zeroed output byte (I67's Question 4). The model reproduces it because it interprets the same code.

## Questions for the human

- **Q-I85-a (the decoder boundary).** `DecodeTxsFromBytes` is answered by the real library. Its own stream rules are therefore the library's, not the model's: a zero type byte ends the stream, and its size checks apply. O8 concerns trailing payload. Should I39b extract it, which needs an oracle for go-ethereum's RLP and typed-transaction decoding at its helpers' call sites? Or is "the stream decoder is environment" an acceptable premise of the O8 pair?
- **Q-I85-b (blob hashes).** The product hashes a blob with a stand-in (0x01, then bytes 1..31 of its sha256), not KZG. O8's HypC binds the blob through its versioned hash. Should I39b compute real versioned hashes through the oracle and go-ethereum's `kzg4844`?
- **Q-I85-c (I39's prereg).** P3 makes F11's L1-count observation visible: `NumL1Messages` is never read. The product records show consistent payloads only, and the random corpus has no mutation that moves the last block number or adds trailing transactions. I39b's prereg should disclose what I85's records show. Do you want I39's counted predictions limited to what I85 does not show?
- **Q-I85-d (R4 against G4).** The forbidden token is `morph`; the key G4 prescribes is `"morph_commit"`, the replay-report convention of M0_SPEC §8. I propose that a later key's contract exempt that replay-key convention from its forbidden-token scan. For I85, either accept R4 as missed, or have the lead add an amendment line (an I85 commit cannot, under R2).
- **Q-I85-e (version 0 commits).** Should I39b or a later key state "every commit the Rollup accepts at the head is derivable" as a PAR-domain law? Its witness would be any version 0 commit.
- **Q-I85-f (a Bend product model).** AGENTS rule 5 has the refuter evaluate claims on the compiled Bend model. The product here is evaluator-level: the extracted Solidity model plus an SSA interpreter. Should I39b compile the consumer to Bend? That means generating Bend from the SSA, with loops as fuel-bounded recursion. Or should it state its laws over the evaluator-level product, with Bend counter-laws only over the extracted parts each law needs?
