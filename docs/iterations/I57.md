## The adversarial phase (run by the builder, no subagent)

**Before the freeze** (folded into the key, `thresholds.adversarial_prereg`):
- **A1, coverage by volume.** Coverage is covered / (222 + new laws), so about 75 covered copies of one law would reach 0.25. Folded: one law per (rule, subform, module), and the law set is fixed at four. A copy per indexed base law would have added 8 laws with no content.
- **A2, a fitted W.** Folded: W and d are cited premises, and R6 checks them against the pin.
- **A3, self-declared provenance.** Not closable. See below.
- **A4, a d = 0 module.** Not a module of this key.
- **A5, family mismatches.** Not closable here. See the Questions.
- **A6, constructed negatives.** Disclosed (E-G9).

**After the observations, on the committed sets:**
1. **A fitted W validates.** With W anywhere in 336 066–337 000, `env-da-retention` passes R1–R5 with every slice at 1.0. Only R6 rejects it, and R6 rests on the key having been written before the data. A later key that pins a W read off this set would validate on the data it was fitted to. Fresh observations are needed for any re-pinned W.
2. **A forged set is admitted.** I copied `obs-fetch-archive`, set every `observed` to `committed`, and kept the producer, sha256 and reads. The G3 rule admits it. The rule pins the tool, not the bytes the tool wrote; nothing offline can tell a hand edit from a run. Mitigations: each set is committed alone, by the tool's command. Residual risk: E-G8, and a question.
3. **A d = 0 module is not exposed by this data.** With zero non-canonical heads in 300, a d = 0 module would also fail R5 here. A4's concern, that R4's 0.95 bar cannot see a rare-event model, stands on paper but was not demonstrated.
4. **The law and the module come apart.** `L_env_fact_da_window` (delivery for age ≤ W) holds on history and replays as passed, yet its module is not validated, because the family claims an exact edge. L9 counts this law as uncovered although its premise is true of the data. The family, not the law, is wrong.
5. **Replay "absent" is not a pass.** I checked the code path: a pair with no observation in its region is unreplayed, not counted.

## Surprises

1. **publicnode refuses `eth_getLogs` beyond about 10 000 blocks** ("Archive requests require a personal token"). I59 had read logs over its whole window. The DA sampler therefore places samples through the archive's transaction listing (`/transactions?to=…&startBlock=…`). The listing only places a sample; the blob hashes, timestamps and observations come from the RPC and the beacon. This was found and folded before the prereg.
2. **The served retention is about 2.57 × the minimum, with a sharp edge** (above). The exact-window family cannot validate a source that keeps more than the minimum.
3. **No reorg was seen at all** in one hour (300 heads, depth 0 included), so a finality module of any depth fails R5 on this window.
4. **One amendment** (`spec/M5/amendments/I57.jsonl`). After the required merges of the lead, R1's literal `git diff 95a2288c` listed four files the lead changed (M2/M3 audit bookkeeping). R1 now reads I57's own commits (`git log --first-parent --no-merges`) over the same paths. Its other checks are unchanged.
5. **A tool rename before the prereg.** The audit admits only `spec/M*/lib/`, the prompt and the tests in a prereg commit, so the tool moved from `holon/m5/` to `spec/M5/lib/`. This happened before the prereg commit.
6. **Pre-prereg smoke run.** The tool was smoke-run with n = 3 (and a 30 s poll) into a scratch directory before the prereg, and that data was discarded. The outcomes are listed in the key. The L1 smoke failed at its very end (the file had moved). Its poll and finality logic had run, so I did not repeat it.

## Questions for the human

1. **R5 and finality_depth (I54).** A finality_depth module predicts only "canonical", so R5 (≥ 5 observed false) holds only if the module is wrong at least 5 times. Should a later key let a one-sided family validate from bounds on its error rate instead (e.g. 0 errors in n, with a stated n)?
2. **The window family is exact; DA guarantees are lower bounds.** Should a later key add a family `window_at_least` (predicted retrievable when q − t ≤ W, unscored beyond)? `L_env_fact_da_window` needs only that.
3. **G3 one level down (adversarial 2).** Should observation sets be produced in CI, by a workflow that runs the pinned tool and commits its output, so that their provenance is the runner's and not the builder's?
4. **Base coverage cannot move without regenerating M2/M3 records** with module premises in place of `A-env`. I57 may not do that. Which iteration may, and under which key?
5. **Coverage by volume (A1).** Should a later key weight coverage per basis element, or cap new laws per module, so that copies cannot lift the headline?
