## Done

### 1. Signatures: G2 verifies them, and only against keys the human froze (`holon/statement_diff.py`)

Before: a committed weakening or binding_change line whose acceptance record said `signature: "verified against keys/"`
was taken at its word. A weakening needed nothing more, and a binding_change skipped its equivalence re-check. Nothing
re-verified the signature, so an agent could commit such a claim and bypass AGENTS rule 2 (never weaken a claim) and
F31's equivalence check. Even a fresh line's signature counted against any key in keys/, and keys/ is agent-writable.
No committed line carries or claims a signature (all 263 checked), and keys/ holds no key.

Now:
- **Only a frozen key counts** (`frozen_keys`). A key `keys/<name>` (one plain file name with a KEY_SUFFIXES suffix)
  counts when tools/freeze.py puts it under the freeze (FROZEN_ROOTS names `keys` or the file; read as a literal, never
  executed), FROZEN.sha256 lists it, and its bytes hash to the listed sha256. Agents never freeze (AGENTS rule 1), so
  until the human freezes a key, every signature fails. `check_entry` (weakening, signed binding_change) uses this rule.
- **G2 verifies every committed claim** (`_verify_committed`, `verify_signature_at`). A signature a committed line
  carries, or its acceptance record claims, is verified against the frozen keys as the commit that appended the line had
  them: FROZEN.sha256 at that commit must list the key with the same sha256, and the key's bytes there must match it (a
  key frozen later, or replaced, signs nothing earlier). Key bytes are read with `git cat-file` and imported into a
  throwaway GNUPGHOME under names of their own, so no path from the tree is written anywhere. A failed verification fails
  G2. A binding_change skips its equivalence re-check only for a signature that verifies and that its acceptance record
  names; a committed weakening also needs its auditor review, as `check_entry` requires.

### 2. Each gate re-runs only its own milestone's binding_change proofs (`statement_diff.scan`, `bindings`, CI)

Before (F35): on a git checkout every milestone's G2 re-ran every binding_change line's proof in both kernels, so
gate-M0, gate-M1 and gate-M2 each re-ran the three 7.9 MB M3 proofs (gate-M0: about 28 min on a runner, 2 min before),
and `holon bind`'s check of the change log ran them again.

Now, with the gated milestone named, a committed binding_change line of a law that is not in `laws/<milestone>/` gets
every check of a committed line (acceptance record, kind, facts at the appending commit, a claimed signature) and every
tie of its proof (its artifacts are the files the record hashes; the pair module and LAWS.bend regenerated from the old
model at the bound commit, the new model and the statement; no escape hatch; the old cone; the catalog bridge). Only the
two kernels' runs on its PROOF.bend are skipped; its own milestone's G2 makes them. Such lines are listed in scan's
`elsewhere` and named in G2's note. A line about a law in no milestone (or in several) is re-run in full by every gate.
`bindings._accepted_entries` (behind `check_change_log`, G2's change-log check, and `holon bind`) scans as the
milestone's G2 does. Off git, F35's rule stands (another milestone's line is not checked at all).

CI: G2 on M3 runs in a job of its own, `gate-M3-G2` (`--checks G2`), so M3's proofs are re-run once per CI run and a G2
failure is not hidden by gate-M3-partial, which stays red until G11V passes (Q36). gate-M3-partial is as before.

### 3. The checker's stack (`holon/bend.py`, `holon/gate.py`, `config/holon.json` bend.js_stack_mb)

F33-F35's "the machine stack overflowed" crashes (no verdict; retried under Q34) come from bun's JavaScriptCore stack
cap. Measured with a plain recursion under the pinned bun:

| RLIMIT_STACK | BUN_JSC_maxPerThreadStackUsage | frames before overflow |
|---|---|---|
| 8 MB, 64 MB or 1 GB | default | about 39,900 (the cap, about 5 MB; why F35's `ulimit -s` did nothing) |
| 8 MB | 64 MB or 1 GB | about 64,300 |
| 64 MB | 64 MB or 1 GB | about 523,000 |
| 1 GB | 1 GB | about 8,387,000 |

Every checker run gets the registered stack, in the checker's process only:
- `_env(cfg)` drops every inherited `BUN_JSC_*` option (as it drops `BUN_OPTIONS` and `BUN_CONFIG_*`) and sets
  `BUN_JSC_maxPerThreadStackUsage` to `bend.js_stack_mb` (1024 MB) of the config the run uses;
- `run` and `run_budgeted` start the checker through a launcher (`_spawn_argv`): this interpreter in isolated mode
  (`-I -S`) sets RLIMIT_STACK's soft limit to the same, within the inherited hard limit, and execs exactly the checker
  command. This process's own limit never changes, so its other children (z3, solc, the frontends) keep theirs. Not a
  `preexec_fn`: checks run from threads (holon.gen.eqsearch), where one can deadlock;
- GENV reports the effective stack (`bend.stack_limits`): JavaScript 1024 MB, RLIMIT_STACK 1024 MB, the hard limit.

A larger stack is meant only to let a deep or large file get a verdict instead of a crash. bend2 reports a stack overflow
at its top level (main.ts `book_err`), but it has other catch sites, so F38 does not claim a stack size can never change
a verdict. Every difference observed is crash against verdict, a crash is never a verdict (Q34), and both kernels must
accept.

Evidence:
- a 20000-deep term, `law deep_eq: {f() == 20000n : Nat}` with `f` 20000 nested additions: at a 4 MB stack both kernels
  crash ("the machine stack overflowed"; at depth 3000 both accept at 4 MB, so the crash is depth); at the registered
  stack both accept it, and both reject the false `20001n` (tests_m3/test_f38.py; bend2 and BendTT in 0.1 to 6.5 s);
- the 7.9 MB whole-cone proof of L_sort_realize_rollup_363_4a64383b (binding_change line 261), before the launcher
  (same limits, set in the parent): bend2 five times at load 3 to 4, all ACCEPTED, no crash (230.7 to 233.5 s); BendTT
  (--verdict) once, ACCEPTED (469.4 s). Without the raised stack, the F35 review saw 2 of 3 bend2 runs overflow at load 2
  to 4, and F35 about 7 in 10 at load 6 to 10.

Q34's crash retries stay as a backstop.

## Questions for the human

- **Freeze keys/ with your first key** when you want signed entries: add `"keys"` to `FROZEN_ROOTS` in tools/freeze.py,
  put your public key in `keys/<name>.asc`, run `python tools/freeze.py write` and commit both. Until then no signature
  verifies, by design.
- **Pin FROZEN.sha256's digest where agents cannot write.** The anchor is FROZEN.sha256 and tools/freeze.py: an agent
  editing both consistently still passes `freeze.py check`. `python tools/freeze.py digest` gives the digest to pin (for
  example as a repository variable CI compares, or under branch protection).
