    - a Header is fixed-width fields, each zero, one, max, max − 1, a small value, k low random bytes or full random bytes;

## Surprises

1. **The M0 model does not compile to C with the pinned Bend 2.0.36 (I16-P1 missed).** `bend driver.bend -o driver.c` fails with `Error: an arity over 247`.
   - The C backend (`bend2/comp.ts`, `WIDE = 247`) refuses a compiled segment with more than 247 parameters.
   - A non-tail call made while that many variables are live needs one, for its continuation.
   - The generated Go encoders open the 257-cell header and call `put` once per field while the later fields' cells are still live: 248 cells for `enc_go_v0`, 256 for `enc_go_v1`.
   - `enc_sol`, `view`, the getters and the predicates compile on their own: `enc_sol` never reads the 32 `sequencerSetVerifyHash` cells.
   - `bend/notes/c_probe/wide.bend` reproduces the limit with 248 fields; `wide_control.bend` with 247 compiles.
   - Following the plan's fallback, `.mjs` stays the engine, native.json records the captured error, and every refinement record runs on `.mjs`.
   - No native-only variant of the model was generated: it would not be the artifact the proofs are about (§8.1).
   - The driver itself is sound: on Bend's own lane it agrees with `.mjs` on 569/569 candidates.
2. **Two preregistered tests were amended because I16 fills a pending field.** Both amendments are logged in `spec/M2/amendments.jsonl`, as the prompt anticipated.
   - In `tests_m2/test_records_v2.py::TestRecordsV2.test_pending_fields_name_their_iteration`, only the `refinement_refs == "pending:I16"` assertion is removed.
   - `tests_m2/test_target_agnostic.py::norm_record` now compares a filled `refinement_refs` list as its pinned pre-I16 value `"pending:I16"`. Dropping the key, the prompt's wording, would have changed the bytes and broken the pin.
   - `RECORDS_PIN` is unchanged, so every other field of the 24 records is still pinned.
3. **Every edge agreed with its implementation on the first full run**: 12,737 comparisons, 0 disagreements. Both prereg instruments reproduce every real digest. Nothing was tuned: the corpus rule, sizes and seed were fixed before the first run, and the records reproduce byte for byte.
4. **The refinement runs are fast.** The Go side takes about 14 s for 8,538 inputs; the Solidity side about 24 s for 4,199 inputs (forge compile included). A full `holon refine` takes about 50 s.

It found one regression and two smaller problems, all fixed after the merge:

1. **Regression in `tests_m2/test_i3_review.py::TestG1IgnoresRunLogs::test_gate_logs_do_not_affect_g1`.** The report did not mention it.
   - **Cause.** G1 compared `metrics.json` byte for byte, and `metrics.json` takes `canary_acceptance` from `gate_report.json`. So a gate output that G1 must never compare (I3) decided G1, and G1 depended on the previous gate run.
   - **The conflict.** The two contracts collide: I16 says G1 compares `metrics.json` byte for byte, while I3 says gate outputs never affect G1.
   - **The lead's resolution.** G1 compares every section of `metrics.json` exactly, except the gate-derived ones (`holon.metrics.GATE_DERIVED = ("canary_acceptance",)`).
   - **Result.** The I3 test passes again, and `tests_m2.test_metrics` passes, including the differential G1 test: tampering `laws.total` still fails G1 and names `metrics.json`.
   - The human should confirm this reading of the I16 contract.
2. **The full suites were not run by the implementer.** After the merge they were run on the combined I12+I13+I16 tree; see `docs/iterations/checkpoint_I16.md`.
3. **`native.json`'s note named the arity limit whatever the error was.** It now names `bend/notes/c_probe/RESULT.json` only when the captured reason is the arity limit. Otherwise it points to `reason`.
