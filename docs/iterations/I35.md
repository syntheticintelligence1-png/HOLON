## Surprises

1. **The constructor's value is not in the Go document (W9).** The frontend records stores alone. `NewBatchData`
   builds its value with a composite literal, `&BatchData{blockContexts: make([]byte, 0), ...}`, so the document holds
   no store of it, and W9's check ("a constructor whose stores set every modelled field to an empty make") has no store
   to read.
   - The generator reads this as the zero value in every modelled field: len 0, cap 0, no backing, which an append
     treats as an empty make.
   - It refuses a constructor whose recorded stores set a modelled field to anything else.
   - Two things keep this from changing an outcome:
     - The PROVED laws hold over every model state, not only the reachable ones.
     - The replay starts from the real constructor, and every recorded capacity agreed.
   - Question 1 asks whether the frontend should extract composite literals.
2. **A test defect in my own prereg (P5).** The test read each kernels entry as `k["kernel"]`, but records key their
   kernels by `"name"`, so it raised KeyError on every record. It is amended with a line in spec/M3/amendments.jsonl
   (`5389c71`); the claim is unchanged.
3. **The witness is smaller than the prereg's trace.** The prereg's instrument names a trace of 60-byte contexts (caps
   64, 128, 256). The search's first witness uses 1-byte arguments, so the capacities it checks are all in Go's 8-byte
   class. A-go-growth is therefore checked here at one class only; the oracle's other classes are tested against the
   pinned runtime's table at the prereg.
4. **The compiled model evaluates ite's arms eagerly.** The first growth function recursed under an `ite` and
   overflowed Bend's JS immediate Nats (2^48) on the search's 30th candidate. It was rewritten as a fold whose step
   keeps the capacity once it is reached; the Go semantics are unchanged.
5. **The pinned checker agreed before the outcome run (probe run 41020182415).** A CI-only probe decided the six OWN
   laws on a scratch catalog with the pinned checker. The outcome run reproduced every status.
6. **The catalog number moved to 1.9.** I29 (NAT, brave-wright's lane) hardcodes holon-rules/1.8 in its preregistered
   test. Rule W8 says only "the next free version after I71's", so I35 took 1.9 after I29. No amendment was needed on
   either side.
7. **Search speed.** Evaluating candidates through the generic JSON driver took about 700 s for the 579,195 traces of
   P6, mostly in serialization. The search now enumerates candidates' order inside node (holon/js/ownsearch.mjs). Each
   hit is re-checked in Python, and Bend decides every status. It runs in about 3.5 minutes locally.
8. **The schema did not admit the own term until the self-check.** The build added `t_own` to the IR 0.3 schema's
   `$defs` but not to the term union `$defs.term.oneOf`, so each of the six OWN laws failed the schema at
   `$.statement.claim`. No test of I35's contract validates OWN laws against the schema, and the derive-side checks
   are holon.ir's rules, not the schema, so nothing caught it. The self-check validated the six laws against the
   schema; `9c2e7d4` adds the reference.
9. **No projected re-make was needed in the end.** Before pipeline v2, a catalog bump changed every M3 statement hash.
   I35 then needed a full M3 re-make, so a 1.9 re-make ran on a projected base (I35 with I71's and I29's branches) to
   avoid a second serial one. Under A's hash scheme 2 the bump changes no statement hash. The landing therefore made
   only OWN's six laws, on the real merged tree, and applied none of the projected records.
