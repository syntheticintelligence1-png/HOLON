## Done

### The two instruments

**`python -m holon audit hostile`** (`holon/audit/hostile.py`) is auditor A2. It reads the target commit's tree from a fresh `git archive`, with LFS objects smudged. It runs the real code in scratch copies of the pinned checkout, with the harnesses of `audit/rounds/M2/round2/harness/` copied in:
- `solidity/HolonHostile.t.sol`: one pass per state (bare, genesis, delay, stored), because Foundry's `revertToState` deletes later snapshots;
- `go/holon_hostile_{batch,types,consumer}_test.go`: in-package harnesses that call by name and through reflection;
- `js/batchdata_walk.mjs`: the batch-data model.

The comparisons:
- Each surface compares the real side with the extracted documents, whose path conditions it evaluates term by term, and with the frozen compiled models. `rollup_act` goes through I20's refinement harness.
- Every mismatch gets one of the contract's classes, decided from the documents.
- Every Go panic and Solidity Panic is recorded with its site and status.
- Target findings carry the auditor's reachability note (`harness/consumer_reachability.json`).
- One planted partiality mutant per surface measures the instrument's own sensitivity.

**`python -m holon audit vacuity`** (`holon/audit/vacuity.py`) is auditor A4. It works through every law record and every hypothesis.

*Law records.* For each one:
- It replays the record's inhabitant on the compiled model the record names, after checking the model's sha256 against the record.
- It evaluates the premises. A SORT-site law uses Reach and the model's own `hit_<x>` ghost; the others use `explore.mjs` evaluate.
- It evaluates the site's subtraction operands where the action evaluates them. Every expression is computed by a probe definition that the model's generator emits from the facts and appends to the compiled model. The walk must find evaluations exactly when `hit_<x>` holds (checked).
- It applies the sidecar's degenerate rule, and runs the representative search (`harness/js/vacuity.mjs`, breadth-first, at most 6 actions) where an inhabitant is degenerate.

*Hypotheses.* Each one goes through the round's binding (`harness/hypotheses.json`). The real implementations come from the pinned checkout, the Go module graph and the EVM:
- `harness/go/holon_vacuity_test.go`: header hash, KZG, zstd codec, transaction codec;
- `harness/solidity/HolonVacuity.t.sol`: KECCAK256, codec libraries, Submitter, messenger and queue.

*Canaries.* Three, for its own sensitivity.

`holon/__main__.py`'s `audit` subcommand gains `hostile` and `vacuity`.

## Surprises

1. **R3 misses by one path.** The preregistered count of 223 extracted paths for the 31 Go header methods includes one path no input can reach: BlobCommitHash's inlined default case under its `version < 2` branch. The Go frontend's reasoner (`holon/frontends/go/terms.py` `_intervals`) seeds a lower bound only for `len` and `cap` terms. It never gives a byte-typed `index` its 0..255 range, so it cannot refute `b[0] != 1` once `b[0] < 2` and `b[0] != 0` hold (F-M2-39). The miss stays a miss: the test fails, and nothing was adjusted.
2. **The P13 path is real but not reached by a default node.** The prediction's "a node deriving from L1 stops at batch 2" needs a qualification. Reading the pinned node:
   - **Default configuration.** On its first run, a default node (no `--derivation.startHeight`) pins its start to the latest confirmed L1 block, and the `--mainnet` preset sets no start height. So it never processes batches 2..7575.
   - **With an early start height.** An operator who sets a start height at or below their commits reaches the path:
     - in local mode (the default verify mode), derivation stops at the first of them;
     - in layer1 mode, it stops even earlier, at batch 1. That batch's parent passes, but its blob is the all-zero blob, which `ParseBatch` cannot decompress (T2).
   - **How it stops.** Either way the stop is permanent: the error returns before the L1 cursor is written.
3. **HypZ fails, and mainnet holds its counterexample.** The zstd codec encodes the empty payload as nothing, and decoding nothing, or zeros, fails. Eight mainnet commits (batches 1, 23, 25–28, 271, 310) carry the zero blob and are rejected by `ParseBatch` after its header steps. This was not predicted; P10 only required a verdict. Filed as F-M2-41, with target finding T2.
4. **The first rollup mutant was not detected.** It bumped the first integer constant of the first require of `challengeState` (Rollup.sol:478, constant 0 to 1), and no hostile input crossed that boundary. The mutant was redesigned once, before the run whose records are committed: it now negates the first require whose revert reason a hostile input of that action met. That is challengeState's "only challenger allowed" (Rollup.sol:126), and the mutant is detected with 20 new mismatches (`a2.json` mutants). The corpus was not changed.
5. **The Solidity harness needed one pass per state.** Foundry's `revertToState` deletes every snapshot taken after the one it reverts to, so a single run that switches between four snapshots loses three of them. The harness now builds each state in turn from the bare deployment, and resets the free memory pointer after each item, to stay under the EVM memory limit over 29111 items.
6. **CF-agg passes, but the model and the code apply `agg` to different lists.** The model hashes the whole blob list. The Rollup hashes the blob hashes before the first zero one. On real chains a blob hash is never zero, so this is a low finding (F-M2-42), not a hypothesis failure.
