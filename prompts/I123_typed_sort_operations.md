With I118's fallbacks every stage runs on Aave V3, but 3 documents fall back at the typed runner and at bind, covering
6 of its 8 derived laws. Each fails while the runner generates its typed model (`holon.sorts.model3`): in two a value

(`holon.sorts`, holon-sort-types/0.4, `spec/M3/lib/sort_seeds.json`) and the Solidity and EVM semantics (Q73, Q84).

## The change (opt-in `typed.sort_ops "word"`)

`holon eval holon` writes `sort_ops: "word"` into the typed sidecar it generates when its protocol names it (never into
a hand sidecar); `holon.sorts.typed_sidecar` checks the value; `holon.sorts.model3` compiles that sidecar's documents
with the sort operations of `holon.sorts.sortops`. Without it every model is generated byte for byte as before.

- **W1, the coercion.** A typed value (a refined sort's word) is read as the 256-bit word it occupies by exactly the
  operations whose result is defined on that word: bitwise and, or, xor and not; masks; trunc, sext and wbyte; shifts
  (packing by shift and or); and + and - outside checked code. The result is an unrefined word. Why no law can conclude
  anything about the value sort from it: in the typed model a sort is a nominal wrapper over the word (`T{p: W}`), never
  a predicate on it, so reading the word adds no fact, and the result carries no sort for a law to use; a law over the
  value's sort reads the typed operations the model registers (affine, comparison, realize), which a word-level result
  never registers.
- **S1-S3, the shifts.** From the EVM: the shift amount is the first operand of `shl`, `shr` and `sar` (the IR's
  `["<<", x, n]`, `[">>", x, n]`, `["sar", x, n]`); an amount of 256 or more gives 0 (`sar` 0 for x >= 0, all ones for x
  < 0); `sar` sign-extends from bit 255. From Solidity, every pinned release (0.5.17, 0.6.12, 0.7.6, every 0.8): the
  result of `<<` and `>>` has the left operand's type, truncated to it (the frontend's `trunc` / `sext`); `>>` on a
  signed type rounds towards negative infinity (`sar`; so since 0.5.0); shifts are never overflow-checked, even in
  checked code. The shift amount's type is where the releases differ: 0.8.0 and later reject a signed amount at compile
  time; 0.5-0.7 accept one and revert at run time when it is negative.
- **C1, checked against unchecked.** A checked operation that overflows reverts; an unchecked one wraps. A typed + or -
  whose term a checked `fits` of the same action reads keeps the typed discipline (an ill-sorted one stays refused); one
  outside checked code is the wrapping word operation. A wrapping reading never proves a law over checked code: the
  checked operation's revert is its `fits` check, which the model keeps.
- **R1.** In a document compiled by a release below 0.8.0, a shift by a non-constant amount is refused: the term does not
  record the amount's type, and a negative signed amount reverts there.
- **D1.** A section over the typed model (`holon.undo.trace.Trace` and its subclasses, `holon.gen.symsec`'s SYM section
  among them) that needs a constant shift the model does not define defines it itself, by the model's own builder.
- **Anything else stays refused** (`GenError`): the document falls back (I116/I118's per-document fallback) and its laws
  stay UNKNOWN, never guessed. Runner reasons are never committed (Q72, Q100 (1)(a)).
